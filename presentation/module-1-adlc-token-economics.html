What Module 1 has to leave you able to doM1

The premise

  • You already use agents daily. So this is not a course about whether they work — it is about what a request costs and what decides that cost.
  • Every request where the agent re-learns something your team already knows is paid for twice: once at the meter, once in the answer being wrong.

How Module 1 is run

  • We baseline one real ticket end to end in Lab 1.1 — deliberately without any of the practices in Modules 2–5.
  • That number goes on the board and stays there for two days. The capstone is measured against it.
The test: by the end of this module you should be able to look at any agent session and say where the money went.

Why proxies, and not just the invoice

  • The six on the left are visible in the session, in front of you — no tooling, no admin access, no waiting.
  • Turns and tool calls track spend. Clarifying questions and rework track how much the agent had to guess. Churn and wall-clock are the outcome.
  • Together they move in the same direction as the invoice — and unlike the invoice, you can attribute them to one ticket.

The discipline

  • Same ticket shape, same counting rules, same person counting, before and after. A baseline compared against a differently-measured run proves nothing.
  • Record it where it survives — metrics.md in the repo, not a slide.
If you cannot say where a number came from, do not put it in front of an engineering audience — including this one.

Lab 1.1 — the baseline run, and the number that follows you for two days3

Four rules for a baseline worth having

  • Representative, not convenient. Roughly the size your team closes several of per sprint — not the trivial one, not the epic.
  • Work naturally. Do not perform efficiency because you are being measured. A flattering baseline sabotages your own result on Day 2.
  • Count as you go. Reconstructing the tally from memory always undercounts rework — that is exactly the number the improvement depends on.
  • Put it on the board. Public, unedited, and it stays there until the capstone.
Set the expectation as a range, not a promise. We will report what we actually measure at the capstone — including if it disappoints. That is the difference between a measurement and a sales slide.

Three kinds of task — name it before you choose anything4

Choosing the model: ambiguity against the cost of being wrong4

How to make this a habit, not a slide

  • Say the quadrant out loud before you send the request. Two seconds, and it is the highest-return two seconds in the module.
  • Decompose across quadrants. Most real tickets are one reasoning decision followed by a pile of mechanical work — price them separately instead of running the whole ticket at the top rate.
  • If you are reaching for the strongest model because you are unsure, the real problem is that the task is under-specified. Fix the spec, not the model — Module 5.

Team-level

  • Write the default down. A one-line convention — “mechanical work goes on the fast class unless it touches migrations” — beats every engineer re-deciding privately.
Model choice is a per-task decision, not a per-person preference and not a setting you configure once.

Mode is not a convenience setting — it is a permission boundary4

The context window is a budget — and you are already spending it5

Three questions, before anything enters the window

  • Is it needed every request? Then it does not belong in the chat — it belongs in a file the agent always has.
  • Is it needed sometimes, and large? Then it belongs behind a tool call, fetched only when the task actually needs it.
  • Is it needed only right now? That — and only that — is what the context window is for.

Why this is an economics slide, not a tips slide

  • Everything you leave in the window is re-billed on every later turn. A long session is where cost quietly compounds.
  • The re-discovery tax and window bloat are the same problem seen twice: facts arriving through the most expensive route available.
The skill is deciding placement — context, file, or tool call. Volume management is what you do when you never made that decision.

The placement rule — context, a file, or behind a tool call5

Session hygiene — compaction is not the same as starting clean5

The preventative habit

  • Write the conclusion out while it is still sound — into the spec, the ADR, the instruction file. Then start clean without losing anything.
  • If the durable artifact is on disk, a fresh session is free. If it only exists in the transcript, you are hostage to a window that is quietly degrading.
  • This is the bridge to Module 5: the spec is the thing that survives the session, and the transcript is disposable by design.

What people get wrong

  • Treating a long session as an achievement. It is not continuity — it is accumulated liability.
  • Re-prompting harder when the real problem is that the session is past its useful life. No prompt fixes a degraded window.
“Ignore what I said earlier” is not an instruction. It is a diagnosis — and the remedy is a new session, not a firmer tone.

Interactive and delegated — where your attention actually goes6

Choosing per ticket — four gates, in this order6

Read the gates as a sequence

  • They are ordered by how often they are the blocker. Gate 1 fails most often, and when it does, the other three are irrelevant.
  • Any single failure sends the ticket to interactive. This is not a scoring system — there is no passing average.

The progression that matters

  • These gates get easier to pass as the course goes on. Module 2 supplies the standing context, Module 3 the precision, Module 5 the machine-checkable acceptance criteria.
  • So a ticket that must be interactive today may be safely delegable by tomorrow afternoon — and that shift is itself part of the argument this course is making.
Delegation is not a maturity badge. An experienced engineer choosing interactive for an ambiguous ticket is making the correct call, not a timid one.

What Module 1 hands to the rest of the courseM1

Four decisions you now owe on every request

  • What kind of task is this? Mechanical, reasoning, or review — named before anything is sent.
  • What mode? The blast radius you are authorising, chosen and not defaulted.
  • What goes in the window? And what should have been a file or a tool call instead.
  • Interactive or delegated? Four gates, and gate one is the honest one.
None of these are new work. You were already making all four — implicitly, and by habit. The change is making them deliberately, and being able to say why.
The line to leave with: the agent will never tell you what it did not know. It will produce something anyway — which is exactly why the number on the board exists.

Q1 · Answer1 of 8

Moving from SDLC to ADLC, what actually changed?
AThe outer loop has to be redesigned around the agent.
BReview becomes less important, because the model is more consistent.
CThe outer loop is largely unchanged; producing code stopped being the bottleneck, and assembling context and verifying output became one.

Q2 · Answer2 of 8

Why is the re-discovery tax “paid twice”?
AOnce in visible spend — turns, tool calls, AI credits — and once invisibly, when the agent guesses rather than stalling and the guess reaches the codebase.
BReading the repository, then re-reading after compaction.

C is a genuine cost of AI-written code — it is Module 8’s subject — but it is not what re-discovery means. D is a procurement view; it never sees the accuracy loop at all. Both loops share one cause, which is why one intervention drains both.

Q5 · When you choose ask, edit or agent mode, what are you deciding?5 of 8

What does the choice of mode actually determine?
AHow much context the agent is allowed to read from the repository before answering.
BWhich model tier serves the request, and therefore what the request costs.
CHow capable the response will be — agent mode reasons harder because it can take multiple steps.
DHow much of the repository you have authorised it to change without asking you again — the blast radius.
Show of hands on each option before advancing · answer on the next slide

Q5 · Answer5 of 8

What does choosing a mode actually decide?
AHow much context it may read.
BWhich model tier serves the request.
CHow capable the response will be.
DHow much of the repository you have authorised it to change without asking again — the blast radius.
D. Mode is a permission boundary. Ask changes nothing, edit changes what you pointed at, agent decides for itself what to touch and can run commands. Escalate only as far as the task needs. C is the most useful wrong answer here — it is precisely the belief that makes people run everything in agent mode out of habit, then spend their scarcest resource, reviewer attention, supervising work that never needed it. The model is the same; only the authorisation changed. A and B are separate decisions. Mode sets the blast radius · model sets the reasoning · context sets the accuracy — three decisions, made on purpose, every time.

ABehind a tool call — fetched only on the requests that actually need it, so the cost is paid on those requests alone.
BIn the repository instruction file, so the agent always has it and never has to go looking.
CPasted into the chat at the start of every session, so it is present before the agent needs it.
DSummarised into three bullet points in the instruction file, and the full document deleted to avoid drift.
Show of hands on each option before advancing · answer on the next slide

Q6 · Answer6 of 8

Where does a large, occasionally-needed document belong?
ABehind a tool call — fetched only on the requests that need it.
BIn the repository instruction file, always present.
CPasted into chat at the start of every session.
DSummarised to three bullets, full document deleted.
A. Frequency crossed with size decides placement. Occasional and large means the cost should fall only on the requests that need it — which is why Day 2 pulls tickets and pages over MCP rather than holding them as standing context. B is placement error two: a permanent charge on every request for material used once in ten, and the signal you did need is now buried. C is placement error one — the re-discovery tax paid by hand; you have become the retrieval system. D is half right and the dangerous half is the deletion: a pointer plus a summary is good practice, destroying the source is not. Both errors feel like diligence, which is why they survive in disciplined teams.
