Two failures survived Module 3. Both need the same thingM4

Where we are

  • Module 3 closed the invented API and scope drift. It could not close the confidently wrong refactor or the test written to pass.
  • You answered why in the quiz: a session cannot audit its own reading of the requirement, because the reading is the thing in question.

The honest cost

  • Four agents cost more per ticket — more wall-clock, more orchestration, four definitions to maintain.
  • What you buy is that agreement between two of them now carries information. Nothing else in this course buys that.
None of this would be needed if verification were cheap. It is not — and Module 1 said so on the first morning, when it priced review as your scarcest resource.

Three reasons — and not one of them is “narrow agents are smarter”1

Deliberate blindness — what each agent is not given1

Four, not nine — the test for whether a role is real1

Four is not a magic number

  • It is the count of genuinely distinct jobs between a ticket and a merged pull request — and this course stops at the merge, deliberately.
  • Distinct means three things differ: the inputs, the definition of done, and the failure modes.

The test, applied to the one everybody proposes

  • A documentation agent takes the same inputs as the coding agent and is judged the same way — does the artifact match the change?
  • Same inputs, same done, same failures. So it is a step in the coding agent's output contract, not a role.
Two agents that would take the same inputs and be judged the same way are one agent with two prompts — and you now maintain two files that will disagree.
Every agent is a definition somebody owns. Nine agents is nine files, drifting at nine different rates — which is the last section of this module.

Seven parts — and the two nobody writes2

Anatomy of a real one — review.agent.md2

.github/agents/review.agent.md--- name: review description: Adversarially review a change set. Blind to the coder's rationale by design. version: 5 owner: payments-platform --- # Role You look for what is wrong, and for what is missing. Your value is that you did not write this and have not been told why. # Allowed tools Read, search, run the tests. No edits - you report, you do not fix. # Inputs - The diff. - The ticket and its acceptance criteria. - docs/adr/, conventions, instructions. Not the coding agent's summary or rationale. That is deliberate. # Never - Never fix what you find. - Never accept "the tests pass" as evidence. - Never soften a finding because the change is otherwise good.

The guardrails are an ordered list, and that matters

  • 1 acceptance criteria · 2 scope · 3 ADRs and conventions · 4 would the tests fail against the old code · 5 what is missing.
  • Five is last because five is what gets skipped — by humans and agents alike. Both are drawn to what is on the screen, and an absent error path is on nobody's screen.

Two lines doing structural work

  • “No edits” is a permission, not a preference. A reviewer that fixes what it finds is an author, and the independence is gone.
  • The withheld input is named in the file. Written down, a deliberate blindness survives the helpful colleague who would otherwise quietly restore it.
Note what is not here: no instruction to be thorough, careful or rigorous. Adjectives do not survive contact with a real diff. Named checks and named prohibitions do.

The four, at a glance3

The test agent — the ticket is the source of truth, not the diff3

Why the report, and not just the tests

  • A suite tells you what was written. A report tells you what was not — and the uncovered criterion is the one that reaches production.
  • Criteria it could not cover are listed, never quietly dropped. A test agent that silently narrows the ticket has done the most expensive possible thing.

The guardrail carried over from Module 3

  • Run every new test against the pre-change code first. It is now a written guardrail in test.agent.md, not a habit you hope somebody remembers.
The blindness earns its keep here. The test agent is not shown the coder's rationale — so if the coder misread the ticket, the test is written against the ticket and the two disagree. That disagreement is the whole return on this module.

The review agent — try to refute it, then report what survived3

“Adversarial” is an instruction, not an adjective

  • “Please check this carefully” produces a polite summary and a compliment. Every team that tries this gets it once and concludes the idea does not work.
  • The instruction that works: try to refute the claim that this change satisfies the ticket, then report what you could not refute.

The tell that yours is not independent

  • It has never blocked anything. A review agent that always agrees is a rubber stamp with extra steps.
  • The usual cause is mechanical: it is being handed the coder's summary. Check the inputs before you rewrite the prompt.
The honest limit: it will raise findings that are wrong. That is the correct trade — a reviewer that never cries wolf is one that never barks. Budget for triage; do not tune it into agreeableness.

Design and coding — the boundary that erodes3

Why this boundary and not the others

  • Test and review are protected by what they are not shown. Blindness holds on its own.
  • Design and coding are protected only by a rule about when to stop — and rules erode where blindness does not.

What the coding agent must never do

  • Never change a design decision because a better one occurred to it mid-implementation. Stop and hand back.
  • That is cheaper than the alternative: a diff nobody expected, reviewed by someone holding a spec that no longer describes it.
Watch for this in your own rollout. If your specs stop matching your diffs after a month, nothing broke — this boundary eroded, one reasonable decision at a time.

Artifacts are the interface — and an interface needs a shape4

A worked hand-off — and the disagreement that pays for the module4

spec.md — FROM THE DESIGN AGENT## Recommendation Reversal creates a second posting with the debit and credit inverted, and marks the original REVERSED. ## Why not amend in place docs/glossary.md: "Reversal - a status change on the original posting. We do not delete postings." Amending would remove the record of what was originally instructed. ## Deciding constraint copilot-instructions.md: balances are derived from entries, never stored. So the reversal must produce entries, not adjust a total. ## Open questions - Value date of the reversing posting: the original's, or today's? No ADR. ASKED.

Why this is checkable in thirty seconds

  • Every claim names the file it came from. You verify by opening two files, not by re-reading a session.
  • The open question is raised, not resolved — design stopped rather than choosing.
test-report.md — FROM THE TEST AGENT, WHICH NEVER SAW THE SPECAC1 balances back to pre-posting values NOT MET - reversalRestoresBalances FAILS against the change. AC2 reversal visible after the fact MET - reversedPostingKeepsStatus AC3 second reversal rejected MET - doubleReversalIsRejected ## Note The change marks the original REVERSED but writes no inverting entries, so derived balances are unchanged. AC1 asks for the balances to move back.
Neither agent is broken. They read the same ticket differently — and because they read it independently, the difference surfaced as a failing test this afternoon instead of a reconciliation break in March.
This is the entire return on the module, in one screen. With one agent this disagreement cannot occur — not because it is less likely, but because there is only ever one reading.

Four shapes — and the two places a human must sit5

What four agents cost — and which tickets justify it5

Decide per ticket, with the gates you already have

  • The Module 1 delegation gates still apply, one level up. Gate 1 — can you write down what done means? If not, you need the design agent before anything else.
  • An ADR that already settles the question is a legitimate reason to skip design entirely. That is what Module 2 bought you.

What never gets skipped

  • Review. It is the cheapest of the four and it closes the two failures nothing else could.
  • If you are cutting the pipeline for time, cut design first and test last.
Tomorrow's capstone runs the full pipeline once, end to end — and that number goes on the board next to Lab 1.1. You will find out then what it cost and what it bought.

Three anti-patterns, in the order you will meet them6

Rolling this out — start with review, not design6

Make it somebody's, in writing

  • Owner in the frontmatter. Not a team inbox — a name. Unowned definitions have a first month, not a lifetime.
  • Version it, and review changes properly. One line here changes the behaviour of every future ticket, which is more leverage than most code changes carry.

Measure it, or the argument is taste

  • Count findings the review agent raised that a human would have missed, and defects that reached the branch anyway. Both are countable in a fortnight.
  • If neither moves, say so. That is the standard this course has held itself to since Lab 1.1.
The failure here is social, not technical — one enthusiast, four excellent definitions, nobody else invoking them, and in six weeks it is cited as evidence that agents do not work.

What Module 4 hands forward — and what Day 1 did not doM4

What you now owe, per ticket

  • Decide which agents this ticket needs. Ambiguity against the cost of being wrong — not the full pipeline out of habit.
  • Protect the blindness structurally. The test agent does not read the rationale; the reviewer does not fix. Both are permissions, not requests.
  • Hand off artifacts, not conversations. Five shapes, each judgeable by a human who was not in the session.
  • Put a human at the spec and at the merge. On client money, neither becomes optional.
Everything today happened inside the editor — one repository, tickets pasted in by hand, artifacts in files nobody else can see.
Into Day 2: the pipeline gets connected to where the work actually lives — JIRA at the front, Confluence at the back, more than one repository in the middle. It starts with the thing that makes delegation safe at all.

Same model, same weights, four narrow roles instead of one broad one. Where does the improvement actually come from?
AEach agent sees less, and is asked to optimise one thing — so the check on the work is genuinely separate from the work.
BFour passes over the same code means more total scrutiny, and more scrutiny finds more defects.
CA narrow agent performs better at a narrow task than a general one does — specialisation improves capability.
DSplitting the work into four smaller requests keeps each context window short, which reduces errors.
Show of hands on each option before advancing · answer on the next slide

Q1 · Answer1 of 8

Where does the improvement come from?
AEach sees less and optimises one thing — so the check is genuinely separate from the work.
BFour passes means more total scrutiny.
CA narrow agent is better at a narrow task.
DFour shorter context windows reduce errors.
A. The gain is structural: context pollution, conflicting goals and reviewer independence. The two failures Module 3 could not close were failures of independence, and independence is the one thing a single session cannot manufacture. C is the intuitive answer, it is false, and it is the one people repeat to their teams — so kill it now. Same model, same weights; telling it that it is a specialist does not make it more capable. B would predict that running one agent four times works equally well. It does not, because all four passes share a reading. D is a real effect and much smaller than the structural one — and it would not close either surviving failure.

A documentation agent — role, or step?
AA role — a different skill.
BA role — knowledge currency matters.

BNever — the named prohibitions, including “never change a design decision; stop and hand back”.

You are wiring up the hand-off into the test agent. Which of these must you withhold, even though passing it would be easy and would seem helpful?
AThe acceptance criteria — it should derive expected behaviour from the code, so the tests match what was built.
BThe public surface of the code under test — otherwise its tests are coupled to implementation detail.
CThe house test conventions — they belong to the coding agent, and repeating them wastes context.
DThe coding agent's summary of what it changed and why.
Show of hands on each option before advancing · answer on the next slide

Q4 · Answer4 of 8

What must be withheld from the test agent?
AThe acceptance criteria.
BThe public surface of the code.
CThe house test conventions.
DThe coding agent's summary of what it changed and why.
D. That rationale is the reading you are trying to check. Given it, the test agent writes tests that confirm the coder's interpretation — and you are back to two things agreeing because they had to. A inverts the module: the criteria are the test agent's source of truth, and deriving tests from the code instead is the test-written-to-pass failure, industrialised. B is needed to write a test at all — the discipline is asserting behaviour through that surface, not being blind to it. C is how you get a @SpringBootTest in a codebase that forbids them.

BWait for a larger sample.

AThat the review agent found no findings — a clean review is the condition for merging.
BThat a review report exists and is attached to the change — including one that says it found nothing.
CThat the review was thorough — the report covers all five checks in the definition's order.

Q6 · Answer6 of 8

What should the gate check?
AThat the review found no findings.
BThat a review report exists and is attached — “nothing found” is a valid report.
CThat the review was thorough.
DThat a human recorded a decision on each finding.
B. Gate on what CI can actually enforce. The existence of an artifact is machine-checkable; the quality of a judgement is not. A is the dangerous one: gate on zero findings and everybody now has a reason to prefer a quiet reviewer — and within a month someone will have tuned it into agreeableness, rationally. C cannot be checked by a machine without becoming a formatting rule that a thorough review can fail and a lazy one can pass. D describes the human gate, which is real and sits at the merge — it is simply not the thing CI enforces.

Q7 · Answer7 of 8

Which anti-pattern is fatal?
AAgent sprawl.
BOverlapping roles.
CHuman gates in the wrong place.
DDefinitions nobody maintains — applied automatically, on every ticket, without being opened.
D. A stale definition is worse than no definition. It produces plausible output, so nobody re-reads it — and it is applied to every ticket without a human ever opening the file. It is Module 2's stale-file problem, with automation attached. A is wasteful and visible — unused files are obvious.
