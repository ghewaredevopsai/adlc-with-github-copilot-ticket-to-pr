Two failures survived Module 3. Both need a separate checkerM4

Where we are

  • Module 3 could not fix two failures: the confidently wrong refactor and the test written to pass.
  • The reason: an agent cannot check its own understanding of the ticket.

The cost

  • Four agents take more time and more requests per ticket.
  • In return, when two agents agree, it means something.

Words used in this moduleM4

Agent words

  • Custom agent — an agent you define yourself, with its own job and rules.
  • Agent file — where that definition lives: .github/agents/<name>.agent.md.
  • Role — the one job an agent does: design, coding, test or review.
  • Rationale — the coding agent’s own explanation of why it wrote the code.
  • Independent — did not write the work, and was not told why.

Pipeline words

  • Artifact — a file one agent hands to the next.
  • spec.md — the design agent’s written plan for the change.
  • Orchestration — deciding which agent runs when.
  • Human gate — a point where a person must approve.
  • AC1, AC2… — acceptance criterion 1, 2 of the ticket.

Three reasons four agents beat one — and “smarter” is not one1

Deliberate blindness — what each agent is not given1

Four agents, not nine — how to tell if a role is real1

Why four

  • Four different jobs sit between a ticket and a merged PR.
  • Different means: different inputs, a different “done”, different ways to fail.

Example: a documentation agent

  • Same inputs and same “done” as the coding agent.
  • So it is a step in the coding agent’s job, not a new role.
Every agent is a file someone must keep up to date. Nine agents means nine files going stale.

Seven parts of an agent file — and the two nobody writes2

A real agent file — review.agent.md2

.github/agents/review.agent.md--- name: review description: Find what is wrong or missing in a change. Blind to the coder's rationale by design. version: 5 owner: payments-platform --- # Role You look for what is wrong, and for what is missing. Your value is that you did not write this and have not been told why. # Allowed tools Read, search, run the tests. No edits - you report, you do not fix. # Inputs - The diff. - The ticket and its acceptance criteria. - docs/adr/, conventions, instructions. Not the coding agent's summary or rationale. That is deliberate. # Never - Never fix what you find. - Never accept "the tests pass" as evidence. - Never soften a finding because the change is otherwise good.

Its checks, in order

  • 1 criteria · 2 scope · 3 ADRs · 4 do the tests fail on the old code? · 5 what is missing
  • Number 5 is last because everyone skips it. Missing things are not on the screen.

Two important lines

  • “No edits” is a permission. A reviewer that fixes things becomes an author.
  • The withheld input is written down, so nobody adds it back by mistake.
No “be thorough” or “be careful”. Named checks and named “nevers” work. Adjectives do not.

The four agents, at a glance3

The test agent — it works from the ticket, not the code3

Why a report?

  • Tests show what was checked. The report also shows what was not.
  • Criteria it could not cover are listed, never dropped.

A rule from Module 3

  • Run every new test on the old code first. It must fail. Now this rule is written in test.agent.md.
The test agent never sees the rationale. If the coder misread the ticket, the test and the code disagree. That disagreement is the point of this module.

The review agent — ask it to disagree3

How to ask

  • “Please check carefully” gets a polite summary.
  • Better: “Try to prove this change does not meet the ticket. Report what you could not disprove.”

Warning sign

  • It has never blocked anything.
  • The usual cause: it is given the coder’s summary. Check its inputs first.
It will raise some wrong findings. That is fine. Do not tune it to always agree.

Design and coding — the boundary that wears away3

Why this boundary breaks

  • Test and review are protected by what they cannot see.
  • Design and coding are protected only by a rule. Rules get bent.

The coding agent must never

  • Change a design decision because it found a better idea. Stop and hand back.
Watch for this: if your specs stop matching your code after a month, this boundary has worn away.

Agents pass files, not chats — and each file has a fixed shape4

A worked hand-off on GB-151 — and the disagreement that pays off4

spec.md — FROM THE DESIGN AGENT## Recommendation Reversal creates a second posting with the debit and credit swapped, and marks the original REVERSED. ## Why not change it in place docs/glossary.md: "Reversal - a status change on the original posting. We do not delete postings." Changing it in place would lose the original instruction. ## Deciding rule copilot-instructions.md: balances are calculated from entries, never stored. So the reversal must create entries, not adjust a total. ## Open questions - Value date of the reversing posting: the original's, or today's? No ADR. ASKED.

You can check this in 30 seconds

  • Every claim names its source file.
  • The open question is asked, not guessed.
test-report.md — FROM THE TEST AGENT (NEVER SAW THE SPEC)AC1 balances back to pre-posting values NOT MET - reversalRestoresBalances FAILS against the change. AC2 reversal visible after the fact MET - reversedPostingKeepsStatus AC3 second reversal rejected MET - doubleReversalIsRejected ## Note The change marks the original REVERSED but writes no reversing entries, so the calculated balances do not change. AC1 asks for the balances to move back.
Neither agent is broken. They read the ticket differently. Because they worked separately, you see it today as a failing test — not months later as a wrong balance.
With one agent, this cannot happen. There is only one reading.

Four ways to run the agents — and two places a person must sit5

What four agents cost — and which tickets are worth it5

Decide per ticket

  • Can you write down what “done” means? If not, start with the design agent.
  • An ADR already answers it? Skip design.

Never skip

  • Review. It is cheap, and it fixes the two failures nothing else could.
  • Short on time? Cut design first, test last.
In tomorrow’s capstone you run all four once. The result goes on the board next to Lab 1.1.

Three common mistakes, in the order you will meet them6

Rolling this out — start with review, not design6

Give it an owner

  • A named person in the file header. Not a team mailbox.
  • Review changes carefully. One line affects every future ticket.

Measure it

  • Count issues the review agent found that a person would have missed.
  • Count defects that got through anyway.
If the numbers do not move, say so — the same standard as Lab 1.1.

What Module 4 hands forward — and what Day 1 did not doM4

On every ticket

  • Choose which agents this ticket needs.
  • Keep the blindness: the test agent never sees the rationale; the reviewer never fixes.
  • Pass files, not chats.
  • Put a person at the spec and at the merge.
