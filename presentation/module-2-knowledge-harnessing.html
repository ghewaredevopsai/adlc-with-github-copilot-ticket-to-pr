Words used in this moduleM2

Knowledge in the repo

  • Standing context — knowledge saved in the repo that the agent reads by itself, every time.
  • Instruction file — a Markdown file Copilot loads automatically. The main one is .github/copilot-instructions.md.
  • Path-scoped instruction file — loaded only when the agent works on files in one folder.
  • ADR (Architecture Decision Record) — one decision, why it was made, and what was rejected.

Ideas we keep using

  • Re-discovery tax — turns the agent spends working out what the team already knows (Module 1).
  • Module map — a table of which package holds what, and what it may use.
  • Bloat — text the agent does not need. It hides the useful lines.
  • Stale — a document that was true once, but is not now.

Tip for facts that change

  • Write where to find it, not the value.
  • “Versions are in pom.xml” stays true. “We use Spring Boot 3.5.3” soon goes wrong.

The six files that hold team knowledge — and what each is not2

A real repository instruction file2

global-bank-account/.github/copilot-instructions.md # Global Bank Account Service — working agreement Moves client money between accounts. Every posting writes two matching ledger entries, or fails. There is no half-finished posting. ## Read these before proposing a change - docs/architecture.md — what lives where - docs/conventions.md — how we write code here - docs/glossary.md — what our words mean - docs/adr/ — decisions already made Check for an existing ADR before designing anything. ## Non-negotiables - Money is a long in minor units (paise/cents). Never double, float or BigDecimal. See ADR-003. - Every posting writes exactly two LedgerEntry rows. - Balances are calculated from entries, never stored. - Constructor injection only. - No Lombok. See ADR-005 — removed on purpose. - Postings between two currencies are rejected. ## When you are unsure Say so and ask. Do not invent an account id, a currency code, a status value or a limit. Quote the file you are relying on when you propose a change.

Three parts, in this order

  • Where to look. It points to other files. It does not try to hold everything.
  • Never break these. Six rules. Breaking one is a bug.
  • When unsure, ask. The part most teams leave out.

Two details to copy

  • “Never double, float or BigDecimal” — name the wrong answers too.
  • “Quote the file you are relying on” — you can see where each answer came from.
Without “ask”, the agent always produces something — even a guess.

Path-scoped instructions — rules for one folder only2

How it works

  • The applyTo line in the file header names a folder pattern.
  • Copilot loads the file only when the agent works on matching files.
  • So test rules cost nothing when the agent is not touching tests.

The rule

  • Write only what is different from the repository rules. Never copy them.
  • The three files below disagree with each other — and each is right in its own folder.
.github/instructions/tests.instructions.md --- applyTo: "src/test/**" --- # Tests - Slice tests, not @SpringBootTest. Service tests use @DataJpaTest with @Import of the services under test. Controller tests use @WebMvcTest. - Assertions use AssertJ, not JUnit's Assertions. - Test names describe the behaviour: rejectsACrossCurrencyPosting, not testPost2. - Write amounts with an underscore before the last two digits — 12_34L is £12.34 — so a factor-of-100 mistake is easy to see. - A test that only checks "no exception was thrown" is not a test. Check the ledger entries.

Try it on your own file

  • Most teams can delete about a third.

Written is not the same as reachable4

Three simple ways to make knowledge easy to find4

1 · A module map

  • Which package holds what, and what it may depend on.
  • Stops the agent from breaking the layering.

2 · An index

  • docs/adr/README.md lists every ADR in one line. One file open, not four.

3 · Clear file names

  • The agent sees the name before it opens the file.
Name each file for the question it answers — not for a meeting or a date.

Treat knowledge like code — or it goes stale5

Why docs go stale quietly

  • No test fails. No alert fires.
  • The first sign is the agent doing something the team stopped doing months ago.

Owner, in the file

  • Name one person. “The team owns it” means nobody does.
  • Add the date it was last checked.
“People will update it” is not a plan. You need a habit a machine or a reviewer checks.

The same-PR rule — and checks a machine can run5

Never put a secret in the most-read file in the repo6

Why a pointer is better

  • It tells the agent where to get the secret.
  • It stays true when the secret changes.

What really leaks

  • Not keys — real client data pasted in as an example.
  • Use fake data, like ACC-CLIENT-001.
Before you commit, ask: would I be OK seeing this line in a PR, a log, and a colleague’s chat? It will be there.

Where one line in an instruction file really goes6

What to take into Module 3M2

Every time you write a fact down

  • One layer only. Two copies will soon disagree.
  • Only if it helps. Otherwise let the agent read the code.
  • Easy to find. A clear name, and a link to it.
  • An owner and a check. Or it goes stale.
Often this means writing less. A short file people trust beats a long one they do not.

Where does this rule belong?
AThe repository instruction file
BA path-scoped file on domain/**
CAn organisation-wide standard
DThe prompt, when a ticket needs it
B. Test 1: true in one repo, so not organisation. Test 2: needed only in one folder, so path-scoped. This is domain.instructions.md in the example. A works but wastes space on every request, and the file slowly grows to three pages. C sounds careful, but hands the rule to a team outside yours, so you can no longer change it. D is the re-discovery tax paid by hand: you type it forever and forget it once.

Q2 · Answer2 of 8

What can an ADR hold that the code cannot show?
AWhich package may depend on which
BWhy this design beats the obvious one
CWhat our business words mean
DThe option that was considered and rejected
D. ADR-007: any engineer — and the agent — reaches for an Idempotency-Key header. It is wrong here because two upstream systems drop the header when they retry, and nothing in the repo says so. A and C can be worked out, slowly — write them down for speed. B is the close one: the code shows the design working, but not that it is better than an option nobody built. Writing down what can be worked out buys speed. Writing down what was rejected buys correctness.

Q4 · Answer4 of 8

Why is a stale document worse than no document?
AIt uses up context space on every request
BIt gives the agent a wrong fact to copy
CIt stops the agent reading the code
DThe agent then trusts all the docs less
C. With no document, the agent reads the code: slow, but correct. With a stale one, it has an answer, so it stops looking. The right answer in the code is never opened. B is true, but it is the symptom; C explains why the damage is so large. A is a real but smaller cost. D gives the model a judgement it does not make. Note: the stale path is faster. A team that only counts turns would think the stale repo improved.

Q5 · Answer5 of 8

The docs are correct. Why does the agent still guess?
AIt is in a wiki the agent cannot reach
BThe document is too long to read fully
CThe model prefers what it was trained on
DThis task needs a stronger model
A. Written is not reachable. The agent would have to find it by search, and guess your words. This is the normal state of most company knowledge. B can happen, but only once the document reaches the agent — here it never did. C describes what the agent falls back to, not why. D buys a bigger model to fix a missing link: the most expensive non-fix. The fix: move it into the repo, name it clearly, and link to it from the instruction file.

Q6 · Answer6 of 8

Which habit best keeps docs up to date?
AA quarterly review, with a named owner per file
BA ticket every sprint to fix the docs
CCI fails the build if code changes but docs do not
DFix docs in the PR that breaks them
D. It is the only moment when the author still remembers what changed and why. A week later, updating the docs is guesswork, and it loses to urgent work. A and B help a little, but a schedule always loses to delivery pressure. C is the interesting wrong answer: it sounds strict, but it makes people add empty edits under docs/ just to pass. Warn on this; never fail the build.

C. It is a text search in one file: fast, reliable, and it never gets tired. This is the model to copy — a decision written in an ADR, enforced by a test. Q8 · Answer8 of 8

A secret was committed, then deleted an hour later
AIt is contained — only an hour, and the file is internal
BIt is leaked, and the key must be changed
CRewrite git history; no need to change the key
DLower risk than a key in code — it is only docs
B. The instruction file goes into every request, from every engineer. In that hour the key reached the AI provider, chat history, anything the agent wrote, and every teammate’s session. It is also still in git history. D is backwards: a key in code is read only by whoever opens that file; this one is read by everyone. C is the dangerous one — rewriting history fixes the repo only, not chat logs or the provider. A assumes internal means safe. Change the key; do not just delete the line.
