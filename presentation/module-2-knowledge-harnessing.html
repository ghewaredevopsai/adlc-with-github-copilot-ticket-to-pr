The layered model — org → repository → path-scoped → task-scoped1

Routing a fact to its layer — three tests, in this order1

Why this order

  • Scope first, because getting it wrong upward is expensive — a rule that is really about this service ends up in an org standard nobody on your team can change.
  • Frequency second, because it decides repository-wide versus path-scoped, and that is where instruction files get bloated.
  • Volatility last, and it is the one people skip. A fact that changes every sprint does not belong in a file reviewed once a year — it will be wrong more often than right.

The trick for volatile facts

  • Write down the pointer, not the value. “Supported versions are in pom.xml” stays true forever; “we are on Spring Boot 3.5.3” is wrong within a quarter.

The standing-context artifacts — and what each one is not2

Anatomy of a repository instruction file — the real one2

global-bank-account/.github/copilot-instructions.md # Global Bank Account Service — working agreement Double-entry payment posting for client money. Every request either produces a balanced pair of ledger entries or fails. There is no partial posting. ## Read these before proposing a change - docs/architecture.md — what lives where - docs/conventions.md — how we write code here - docs/glossary.md — what our nouns mean - docs/adr/ — decisions already made Check for an existing ADR before designing anything. ## Non-negotiables - Money is a long of minor units. Never double, never float, never BigDecimal. See ADR-003. - Every posting writes exactly two LedgerEntry rows. - Balances are derived from entries, never stored. - Constructor injection only. - No Lombok. See ADR-005 — a deliberate removal. - Cross-currency postings are rejected. ## When you are unsure Say so and ask. Do not invent an account id, a currency code, a status value or a limit. Quote the file you are relying on when you propose a change.

Three blocks, in this order

  • The router. Its main job is to send the agent somewhere else. This file cannot hold everything and should not try.
  • The non-negotiables. Six lines. Each one is a rule whose violation is a defect, not a preference — and each traces to something real in the codebase.
  • Permission to ask. The block teams leave out, and the cheapest one to add.

Two details worth copying

  • “Never double, never float, never BigDecimal” — the prohibition is stated three ways. The agent needs the shape of the wrong answer, not only the right one.
  • “Quote the file you are relying on” is free verification: you can see at a glance whether the answer came from the repository or from the model’s prior.
Without an explicit “ask” instruction, the default is to produce something — because producing something is what it is for.

Path-scoped instructions — specific without being expensive2

The mechanism

  • The applyTo glob in the frontmatter is the whole trick: the file is pulled in only when the agent works on matching files.
  • So the test-writing rules cost nothing on the 90% of requests that never touch tests. This is Module 1’s context budget, enforced by the tooling rather than by discipline.

The discipline

  • State only what differs from the repository rules. The moment a path-scoped file restates them, you own two copies that will drift.
  • The three example files genuinely contradict each other — domain says “no framework annotations”, api is entirely about framework annotations. Both are right in their own scope, and that is only possible because they are scoped.
Merging them into one repository file would force the agent to hold rules it cannot use, and to reason about which apply — a turn spent on something the glob answers for free.
.github/instructions/tests.instructions.md --- applyTo: "src/test/**" --- # Tests - Slice tests, not @SpringBootTest. Persistence-facing service tests use @DataJpaTest with @Import of the services under test. Controller tests use @WebMvcTest. - Assertions use AssertJ. Do not mix in JUnit's Assertions. - Test names are sentences describing the behaviour: rejectsACrossCurrencyPosting, not testPost2. - Amounts are written with underscores at the minor-unit boundary — 12_34L is £12.34 — so a misplaced factor of 100 is visible on the page. - A test that asserts only "no exception was thrown" is not a test. Assert the ledger effect.

Signal, bloat, and the third category people forget3

The write-it-down test — inferability against frequency3

Applying it to your own repository

  • Take your current instructions file and put every line in a quadrant. In most teams a third of it is bottom-left and should simply be deleted.
  • For anything top-left, ask whether the honest fix is an index or a module map rather than prose. Structure beats explanation.

The one-line version

  • Write down what the agent cannot work out, and what is expensive to work out. Nothing else.
  • Then write down everything unreachable, whatever the frequency — that is the category the matrix cannot price.
A shorter instructions file is usually a better one. If yours has never had a line removed, it is carrying bloat.

A stale file does not just mislead — it stops the search3

Written is not the same as reachable4

Three cheap structures that turn writing into finding4

1 · The module map

  • Converts an expensive search into a lookup. Highest leverage artifact after the instructions file.
  • The column that earns its place is the last one — what may depend on what. That is what stops the agent proposing a change that violates the layering.

2 · The index

  • The humblest idea here and the most neglected. Without docs/adr/README.md, four ADRs means four file opens to learn that none of them apply.

3 · Navigable naming

  • The filename is the only metadata the agent has before it opens anything.
  • ADR-007-duplicate-suppression.md says what is inside. decisions-v2-final.md says nothing.
Name files for the question they answer — not for the meeting, the quarter, or the person who wrote them.

Knowledge is code — owned, reviewed, and tested, or it rots5

The sentence to take away

  • Knowledge that is not owned, reviewed and tested is not an asset. It is a liability with a deceptive first month.

Ownership, specifically

  • Name a person per artifact, in the file. A team is nobody, and “the team owns it” is how a file reaches month twelve unread.
  • Put the owner and the last review date in the document, where the next reader — human or agent — can see how much to trust it.

Why decay is silent

  • Nothing fails when a document goes stale. No test breaks, no alert fires. That is precisely why it needs a mechanism rather than good intentions.
If your answer to “how do you keep it current” is “people update it”, you have described the failure, not the mechanism.

The same-PR rule — and drift checks a machine can actually run5

The most-read file in the repository is the worst place for a secret6

Why the pointer is genuinely better

  • It tells the agent what to do — resolve it from the vault — rather than handing it something to copy into code.
  • It stays true when the credential rotates. The value would not.

The two that actually leak

  • Not keys. Client and personal data, pasted into a document to make an example concrete — a real account number in a sample request, a real name in a debugging note.
  • Synthetic examples cost nothing and read identically. The examples’ accounts are all ACC-CLIENT-001 for exactly this reason.
The test before you commit: “would I be comfortable if this line appeared in a pull request description, a log, and a colleague’s session?” Because it will.

Where a line in an instruction file actually goes6

What Module 2 hands forwardM2

What you now owe, every time

  • Route it to one layer. Org, repository, path or task — and only one, or the copies will disagree within a quarter.
  • Justify writing it at all. Unreachable, or expensive to infer. Otherwise let the agent read the code.
  • Make it findable. A name that says what is inside, and something that points at it.
  • Give it an owner and a check. Unowned knowledge has a first month, not a lifetime.
Half of this is permission to write less. The shortest instruction file that carries the non-negotiables beats the thorough one nobody trusts.

BWhy the current design beats the obvious alternative.

Which line is bloat?
A“We are on Spring Boot 3.5.3 and Java 25.” — trivially inferable from pom.xml, and wrong after the next upgrade.
BLombok removed deliberately — a negative constraint.

Q4 · Answer4 of 8

Why is a stale document worse than none?
AIt consumes context budget.
BIt gives a wrong fact, which produces wrong code.
CIt terminates the search — the agent has an authoritative answer, so it never opens the code that would have corrected it.
DIt signals poor maintenance, so the agent discounts everything.
C. With no document the agent falls back to reading the code: slow, and correct. With a stale one it stops looking. The correct information three directories away is never opened. B is true but mild — it describes the symptom, and C explains why the damage is disproportionate. A is a real but second-order cost. D ascribes a judgement the model does not make. The consequence worth sitting with: the stale path is faster than the no-document path. A team measuring only turns would score the stale repository as an improvement.

Q5 · Answer5 of 8

Correct knowledge exists. Why does the agent still guess?
AIt is reachable only by search — in a system the agent cannot read, under a title nobody would query for.
BThe document is too long and gets lost mid-window.
CThe model prefers the convention it was trained on.
DIt needs a stronger model.
A. Written is not reachable. Tier 3 — found by search — is the weakest and the most commonly assumed, and it fails whenever the agent would have to guess your vocabulary. This is the ordinary state of most enterprise knowledge. B is a real effect but it presupposes the document reached the context at all — here it never did. C describes what the agent falls back to, not why. D is the Module 1 reflex, and buying a bigger model to compensate for unreachable documentation is the most expensive possible non-fix. The fix is not to rewrite content that is already fine: move it into the repository, name it for the question it answers, and point at it from the instructions file.

BA recurring ticket in each sprint to reconcile documentation against changes made in the previous one.

Q6 · Answer6 of 8

Which mechanism most reliably keeps knowledge current?
AA quarterly review with named owners.
BA recurring reconciliation ticket each sprint.
CA CI job that fails the build when source changes without a docs/ change.
DKnowledge changes in the same pull request that invalidates it, enforced as a review question.
D. It is the only moment when the person changing the code still knows what changed and why. A week later the update is archaeology, and archaeology loses to whatever is urgent. A and B are genuine practices that help at the margin — and both run on a cadence that always loses to delivery pressure. C is the most interesting wrong answer here: it is a sensible-sounding proposal that fails worse than doing nothing, because a hard gate manufactures compliance. Make documentation mandatory to merge and you get documentation-shaped edits — a whitespace change under docs/ — plus resentment. Warn on this signal; never fail on it.

CWhether org.projectlombok has appeared in the POM, which ADR-005 says it never will.

Show of hands on each option before advancing · answer on the next slide

Q7 · Answer7 of 8

Which drift check can a machine run?
AWhether the architecture doc is still accurate.
BWhether the conventions match current preference.
CWhether org.projectlombok has appeared in the POM, contrary to ADR-005.
DWhether an ADR's reasoning still holds.
C. It is a string in a file — decidable, fast, and it never gets bored. This is the shape to aim for: a decision recorded in prose, enforced by a test. A, B and D all require judgement about meaning, which is what the human review cadence is for. The generalisation: every prohibition in your ADRs is a candidate test. If a decision can be violated mechanically, it should fail the build rather than wait for a reviewer who happens to remember the history — because that reviewer eventually leaves. A machine cannot check that a paragraph is true; it can check that the file it names still exists, that the ADR it points at is not deleted, and that the banned thing is still banned.

AContained — only an hour, and the file is internal.
