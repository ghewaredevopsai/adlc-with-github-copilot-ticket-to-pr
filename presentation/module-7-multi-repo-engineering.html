Words used in this moduleM7

Two repos, one API

  • Producer — the service that offers the API. Here: the account service.
  • Consumer — the service that calls it. Here: the transaction service.
  • Contract — what the API accepts and returns, agreed by both sides.
  • Mirrored type — a hand-written copy of a producer class, kept in the consumer.
  • Multi-root workspace — one editor window with both repos open.

Changing it safely

  • Additive change — adds something optional. Old callers keep working.
  • Compatibility window — a period when the old and new shapes both work.
  • Blast radius — everyone affected if a change is wrong.
  • Deprecation cycle — mark it, announce it, wait, then remove it.
  • GB-158 — the lab ticket. It adds an optional settlementDate. If missing, valueDate is used.

The contract file — four questions, answered once2

global-bank-transaction/docs/contract.md — WORKED EXAMPLE# What we depend on in global-bank-account | We call | For | |---|---| | POST /transaction | One call per transfer | | POST /checkBalance | Not used yet | ## The mirrored types feign/AccountFeign's request and response are hand-written mirrors of the producer's types. There is no code generation today; the cost of keeping them in step by hand is accepted, and the discipline that makes it safe is ADR-009 in the producer repository: producer merges first, consumer second, PRs linked. ## Failure semantics we rely on - A rejected posting returns 4xx with an RFC 9457 body whose title is the producer's stable reason string. - The producer is a leaf service, so a timeout means the producer is unhealthy - there is no downstream to blame.

Four questions it answers

  • What do we call? So the agent does not invent an endpoint.
  • Are the types real or copied? So it knows a copy can be out of date.
  • What does an error look like? So it does not invent one.
  • What is the merge order? Copied here on purpose. The consumer cannot see the producer’s ADR.
The real file also explains why @JsonIgnoreProperties protects reads but not writes. An agent cannot work that out — and will not ask.
One page per repo. No tools needed. If you do one thing on Monday, do this.

Contract first, then producer, then consumer3

Why this order

  • Adding an optional field is safe for every existing caller.
  • Sending a new field is safe only after the producer accepts it.
  • Reverse the order, and production breaks for a while.

Why an agent gets it wrong

  • The rule is in the producer’s ADR. The consumer’s agent cannot see it.
  • No diff shows the merge order.
Write the rule in both repos: the producer’s ADR and the consumer’s contract file.

When a change cannot be additive — three options3

Two pull requests, one change — four simple habits4

The template asks

  • Does this change a contract another repo uses? Link the other PR and state the order.
  • Is the PR you depend on deployed? Approved is not enough.
  • Is the change additive? If not, how long is the compatibility window?

What CI can check

  • A PR that touches the contract links to a paired PR.
  • CI cannot check the order. People must.
A good test: can you say which PR to undo first? If not, you have two PRs, not a plan.

Two PR descriptions — the plan lives only in the text4

PR #1 — global-bank-account, merges first
GB-158: add settlementDate to the posting contractAdds an optional settlementDate to the posting request. Absent, it defaults to valueDate, so every existing caller is unaffected. Cross-repo: paired with global-bank-transaction PR #88. This one merges and deploys first. Additive: yes. No compatibility window needed - nothing is required that was not required before. Rollback: safe to revert on its own, provided consumer #88 has not yet merged.
PR #2 — global-bank-transaction, merges second
GB-158: send settlementDate on transfer postingsPopulates settlementDate on each posting. Cross-repo: paired with global-bank-account PR #412. DO NOT MERGE until #412 is deployed - not merely approved. Sending this field before the producer accepts it fails the batch. Verified: #412 deployed to the shared environment, checked by posting one item with the field set. Rollback: revert this first, then #412.
None of these facts is in either diff. Merge order, deploy state and rollback order belong to the pair. A PR has no field for them, so they go in the template.

Four ways to show the other repo without opening it5

An out-of-date contract file is worse than none5

Three cheap habits

  • Same-PR rule. The PR that changes the contract also updates the file. You have seen this rule all course.
  • A CI check. Every endpoint in the consumer’s contract file still exists on the producer.
  • A named owner on both copies.
A stale doc in one repo misleads one team. A stale contract misleads the team that cannot check it.

What belongs in the contract file — and what does not5

The test

  • Would an agent on this side get it wrong without this line? If not, delete it.
  • Shorter is usually better.

Keep the “not used” lines

  • The example says the balance endpoint is “not used yet — reserved for the pre-flight funding check”.
  • So the agent knows the endpoint exists, and that not calling it was a choice.

Shared libraries — a change reaches callers you cannot see6

Library vs service

  • A service change deploys once, when you choose.
  • A library change is picked up by many teams, when they choose.
  • So a compatibility window is your only protection.

Put in the library’s instruction file

  • These three tiers, with an example of each.
  • The version policy, so a breaking change has a visible cost.
Same idea as Module 6’s write-back tiers: can someone see a mistake, and undo it in time?

What to take into Module 8M7

For any change that crosses repos

  • Agree the contract before touching code.
  • Producer first (additive), consumer second. Write the order down.
  • Give the agent a summary, not the whole repo.
  • Keep a human at the merge step.
