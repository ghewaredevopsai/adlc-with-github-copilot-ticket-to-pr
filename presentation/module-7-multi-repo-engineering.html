Four questions it answers before they are asked

  • What do we call? So the agent does not invent an endpoint — and can notice when a diff adds one.
  • Are the types real or mirrored? Knowing the mirror is hand-written is what makes an agent treat it as possibly stale.
  • What does failure look like? So it does not invent an error contract that the other side does not honour.
  • What is the sequencing rule? Duplicated here deliberately, because it binds the side that cannot see the ADR.
Read the last paragraph of the real file: it explains why @JsonIgnoreProperties protects reads and not writes. That is reasoning an agent cannot reconstruct from either codebase — and will not think to ask about.
One page, per repository, and it needs no tooling. If you do one thing from this module on Monday, this is it.

The sequence, and the asymmetry it follows from3

The ordering is not a convention

  • It follows from one asymmetry: an additive producer change is safe for every existing consumer, and a consumer that sends a new field is only safe once the producer accepts it.
  • Reverse the order and there is a window in which the consumer sends a field the producer rejects — in production.

Why an agent gets this wrong

  • The rule lives in one repository's ADR and binds the other. An agent working in the consumer has no way to know it is bound.
  • And nothing in either diff encodes the order. It is a fact about two pull requests, and pull requests have no field for it.
So write it into both. The sequencing rule belongs in the consumer's contract document as well as the producer's ADR — duplicated deliberately, because the alternative is a rule that binds someone who cannot see it.

Not everything can be additive — three honest shapes3

Two pull requests, one change — four cheap disciplines4

What the template asks

  • Does this change a contract another repository depends on? If yes, link the paired PR and state the order.
  • Has the PR this depends on been deployed? Not approved — deployed.
  • Is this change additive? If not, name the compatibility window and how you will know every caller has moved.

What CI can check, cheaply

  • That a PR touching the contract's named files links to a paired PR. Mechanical, and it catches the solo cross-repo change.
  • It cannot check the order — that stays human, and that is why it is written in words.
The rollback question is the good test of whether you sequenced it: if you cannot say which half to revert first, you have two pull requests rather than a sequence.

Two descriptions — and how much lives only in prose4

PR #1 — global-bank-account, merges first

Cross-repo: paired with global-bank-transaction PR #88. This one merges and deploys first. Additive: yes. No compatibility window needed - nothing is required that was not required before. Rollback: safe to revert on its own, provided consumer #88 has not yet merged.
PR #2 — global-bank-transaction, merges second
GB-158: send settlementDate on transfer postingsPopulates settlementDate on each posting. Cross-repo: paired with global-bank-account PR #412. DO NOT MERGE until #412 is deployed - not merely approved. Sending this field before the producer accepts it fails the batch. Verified: #412 deployed to the shared environment, checked by posting one item with the field set. Rollback: revert this first, then #412.
Not one of those facts is in either diff. Merge order, deployment state and rollback direction are properties of the pair — and a pull request has no field for any of them, which is why they go in the template.

Four substitutes for opening the other repository5

A drifted summary is worse than none — and now two teams rely on it5

Three mechanics, all cheap

  • The same-PR rule. A change to the contract updates the summary in the pull request that changes it. This is the fourth time this rule has appeared in two days — that is not repetition, it is the answer.
  • A CI check on the producer side: every endpoint the consumer's contract document names still exists. Runnable wherever the two are built in the same pipeline.
  • An owner, named. Shared knowledge with no owner has a first month, not a lifetime.
Why this matters more here than inside one repository: a stale in-repo document misleads one team. A stale contract document misleads the team that cannot check it — which is the whole reason they were reading it.
And it is read by agents on both sides, automatically, on every ticket, without anyone opening the file. Module 2's argument, one boundary out.

What earns its place — and what guarantees drift5

The test

  • Would an agent on this side get this wrong without the line? If no, delete it.
  • Module 2's write-it-down test, in a new setting — and the same discipline applies: a shorter contract document is usually a better one.

Why the “what we do not call” line is worth keeping

  • The example says the balance endpoint is “not used yet — reserved for the pre-flight funding check”.
  • That single line tells an agent both that the endpoint exists and that calling it is a decision somebody has deliberately not taken. Absence, made readable.
The failure to avoid: a contract document that grows into a second copy of the producer's documentation. It will drift, nobody will notice, and it will be read by agents on both sides.

Shared libraries — the blast radius is everyone you cannot see6

Why a library is different from a service

  • A service change is deployed once and you control when. A library change is adopted N times, by teams on their own schedules, and you control none of it.
  • So the compatibility window is not a nicety — it is the only mechanism you have.

What to put in the library's own instructions

  • The three tiers, named, with an example of each. An agent working there should be able to place its own change.
  • The version policy, and what a breaking change costs — so “just change the signature” has a visible price.
The same tiering as Module 6's write-back, for the same reason: the test is whether somebody can see it went wrong, and undo it, before it hurts them.

Four things, in the order they pay6

What Module 7 hands forwardM7

What you now owe, on a change that crosses a boundary

  • Agree the contract before either side is touched. It is a spec for an interface, and it is not a code change.
  • Sequence it: producer additive first, consumer second — and write the order in words, because no diff encodes it.
  • Give the agent a summary, not a checkout. One page beats tens of thousands of re-billed tokens.
  • Keep a human at the merge gate. Some cross-repo defects are catchable only by someone who knows both sides.
And the thing to do Monday, with no tooling at all: a one-page contract document in each repository, and one question in the pull request template.

AIt reasons about a system it can see half of — and nothing tells it which half is missing.

A. And the second clause is the important one: it does not know it is missing anything, so it does not stop, ask or hedge. B. A date that means receipt on one side and economic effect on the other produces a system that runs perfectly and reports wrong numbers. AThe producer owns the contract, so contract changes should originate on that side.
BThe producer's tests are more comprehensive, so problems are more likely to be caught there first.
CAn additive producer change is safe for every existing consumer; a consumer sending a new field is only safe once the producer accepts it.
DIt matches the direction of the dependency — the consumer depends on the producer, so the dependency ships first.

Q3 · Answer3 of 8

Why producer first?
AThe producer owns the contract.
BIts tests are more comprehensive.
CAdditive producer changes are safe for existing consumers; a consumer sending a new field is not safe until the producer accepts it.
DIt matches the dependency direction.
C. The asymmetry, not the convention. Learn it as the asymmetry and you can apply it to cases this course never showed you. D is the dangerous one because it gives the right order for the wrong reason — and the wrong reason fails on the rollback, where the dependency direction is unchanged but the order reverses: consumer reverts first. A is about ownership, not safety. B is not reliably true and would not matter if it were.

Q4 · You must revert. In which order?4 of 8

Both halves of GB-158 are merged and deployed. Something unrelated forces a rollback of the whole ticket. What goes first?
AThe producer — reverse the order it went in, so the contract change is removed at the source.
BBoth together, in one coordinated window, since the change was one ticket.
CWhichever is riskier to leave in place, judged at the time by whoever is running the rollback.
DThe consumer — stop sending the field before the producer stops accepting it.
Show of hands on each option before advancing · answer on the next slide

Q4 · Answer4 of 8

Which half reverts first?
AThe producer.
BBoth together.
CWhichever is riskier, judged at the time.
DThe consumer — stop sending the field before the producer stops accepting it.
D. Reverting runs the sequence backwards, decided by the same asymmetry. Revert the producer first and you leave a consumer sending a field nobody accepts — which is the exact failure the ordering existed to prevent, arrived at from the other direction. C is what happens in practice when nobody wrote the order down, and it is a judgement made under pressure by whoever is on call. B is a coordinated deploy, which is the shape you sequenced specifically to avoid needing. The corollary worth keeping: if only half of a cross-repo change lands, you want the half that landed to be the producer — it is safe on its own.

Q7 · Answer7 of 8

Which needs the owner?
AA new overload.
BA validation rejecting something already documented as invalid.
CTests and documentation for existing behaviour.
DChanging the default of an existing optional parameter.
D. Every caller who relied on the old default gets new behaviour without changing a line, and none of them will see a compile error. That is the highest-blast-radius change on this slide and it looks like the smallest. The honest answer is that it is a judgement call — which is exactly why the tiering exists, so that judgement is made once, by an owner, rather than repeatedly by whoever happens to be working.
