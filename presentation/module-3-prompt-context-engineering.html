The repository knows what is true. This module is how you askM3

Where we are

  • Module 2 changed what the repository knows. This module changes what you say — and what happens when neither has the answer.
  • The gap this module closes: the agent will produce something whether or not it knows. Grounding is how you make not-knowing visible.

The shape of the module

  • First a shape for the request, then how to stop it inventing, then how to prove one way of asking beats another.
Row three of the tally sheet is measured here — and not in turns. This one is measured as a pass rate over a set of tickets, because that is the only honest way to compare two prompts.

Six parts — and the failure each one prevents1

The same ticket, asked twice — GB-1511

What almost everyone types
THE ORDINARY REQUESTAdd a reversal endpoint for postings.

What it leaves the agent to decide

  • Whether a reversal deletes, mutates, or adds — and Finance already ruled two of those out, in the ticket.
  • Which files are in play, and whether a stored balance column would be helpful.
  • What “done” means, and what to do when it is unsure.
Every one of those becomes a guess you cannot see in the diff — and two of them become rework you counted this morning.
The same request, with the six parts
THE ENGINEERED REQUESTGOAL Add POST /api/v1/postings/{id}/reversal. CONSTRAINTS - Follow docs/conventions.md and .github/instructions/api.instructions.md - Reversal is a status change, not a delete (docs/glossary.md) - Balances are derived; add no balance column INPUTS - posting/service/PostingService.java - posting/domain/Posting.java - GB-151, all six acceptance criteria OUTPUT CONTRACT - Controller + service + slice tests - No new dependencies - Errors as ProblemDetail, kebab-case reason DONE - mvn test green; the new test fails without the change - Second reversal rejected; balances restored STOP - If reversal semantics are ambiguous, stop and ask. Do not choose. - Do not modify existing ledger entries.

Stop conditions — installing the behaviour the model does not have1

Make refusal cheap, or it will not happen

  • Name the circumstance, not the feeling. “Ask if unsure” does nothing; “ask if no ADR covers this” is checkable.
  • Say what to do instead of choosing — stop and list the options, so the turn is not wasted.

Where they come from

  • Your rework column from Lab 1.1. Every rework prompt is a stop condition you did not write.
  • Once written, they belong in a skill file — next section — not retyped per ticket.
The line to leave with: the agent will never tell you what it did not know. Stop conditions are the only way you find out before the diff.

Instructions, skills, prompts — three artifacts, three lifetimes2

The mistake this prevents

  • Procedures leak into the instructions file, which then carries steps nobody needs on most requests — and it grows until it is skimmed.
  • Facts leak into the prompt, which is the re-discovery tax paid by hand, forever.

Why this one is a file and not a habit

  • A good procedure held in one engineer's head is a single point of failure with a notice period.
  • In the repository it can be reviewed, diffed, improved and blamed — like anything else you depend on.
Sequence matters: do Module 2 first. A skill file written over a repository with no standing context just re-states facts, and rots twice as fast.

Anatomy of a skill file — the reusable half, written once2

.github/skills/account-change.skill.md--- name: account-change description: Implement a change to posting or balance behaviour in global-bank-account version: 3 owner: payments-platform --- # Before you write anything 1. Read docs/adr/README.md and open any ADR whose subject the ticket touches. 2. Quote the constraint you are relying on, with the file it came from. # Constraints that always apply - Amounts are long minor units (ADR-003). - Every posting writes exactly two entries. - Balances are derived, never stored. - Slice tests only, never @SpringBootTest. # Output contract - Service method + controller + slice tests. - Errors as ProblemDetail, kebab-case reason. - No new dependencies without an ADR. # Stop and ask — do not choose - Two defensible readings of the criteria. - An architectural choice with no ADR. - Any change to an existing ledger entry.

What the frontmatter is for

  • name and description — how it is found and invoked. Vague descriptions are why skill files go unused.
  • version and owner — what makes it an asset rather than a note. Unowned files have a first month, not a lifetime.

Read the body again

  • It is slide 3's six parts with the ticket-specific slots left empty. Goal and inputs arrive per request; everything else was already true.
  • The stop conditions are the team's counted rework, written where the next person does not repeat it.
The honest caveat: your first version will be too long. Skill files get better by having lines removed after they fail to earn their place on a real ticket — same discipline as Module 2.

What makes it an asset rather than a saved snippet2

Four grounding rules — four different jobs3

Why these work

  • Not because the model obeys. Because they make an invented answer expensive to produce and easy to spot.
  • A citation you can check in one file open changes the economics of your review.

Where they live

  • All four belong in the skill file, not in every prompt. You wrote them once in the last section.
  • In the worked example they are already half-installed: copilot-instructions.md ends with “quote the file you are relying on”.
These are not magic words. A grounding rule with no named circumstance and no verification step is decoration, and it will make you more confident without making the output better.

Grounded and ungrounded — the same question3

Ungrounded — and note that it is not wrong
“HOW SHOULD I HANDLE A DUPLICATE POSTING?”Use an idempotency key. Have the caller send an Idempotency-Key header, store it against the posting, and return the original posting id if the key is seen again. This is the standard approach for payment APIs and it handles gateway retries cleanly.

Why this is the dangerous shape

  • Correct in general, false here — and nothing in the answer tells you which.
  • No claim is attached to a source, so verifying it means re-reading the repository yourself.
  • It is more confident than the grounded answer, because it has nothing to be uncertain about.
Grounded — cite, quote, and name the gap
SAME QUESTION, WITH THE GROUNDING RULES IN THE SKILL FILEDuplicate suppression keys on clientReference + valueDate. Source: docs/adr/ADR-007. It records that a header-based idempotency key was considered and rejected, because the two highest-volume upstream systems do not propagate a client header through their retry path. Existing code: PostingRepository already declares findByClientReferenceAndValueDate, which is currently unused. Not found: what should happen when the same reference arrives with a different amount. No ADR covers it. Stopping to ask.

Four failures — different tells, different counters4

What actually counters each — and how strong it is4

Read the pattern

  • The failures your toolchain catches need nothing from your prompt. Spending words there is the most common waste in an experienced team.
  • The failures that need a human who knows the system are the ones worth designing around — and the ones that justify Module 4.

The one habit worth taking away

  • Read the test before the implementation. If the test would pass against the old code, nothing has been proven and the green tick is worse than no tick.
Where this lands in the labs: Lab 2.6 hands you a change set containing one real defect and one hallucinated API. The review agent catches one of them. Which one it misses is the lesson.

Tests written to pass — why the green tick can be worthless4

The mechanism, plainly

  • Ask for the change and its tests in one request, and the tests are generated from the same understanding as the implementation — including the same misunderstanding.
  • The test is not an independent check. It is a restatement.
  • So a misread requirement produces a defect and a passing test that defends it.

Three tells you can spot in seconds

  • It asserts no exception was thrown, and nothing else.
  • It asserts the mock was called — a test of the code you just wrote, not the behaviour you wanted.
  • It re-states the implementation. Change the implementation legitimately and the test fails: that is a change detector, not a test.
The example already says this — tests.instructions.md: “A test that asserts only ‘no exception was thrown’ is not a test. Assert the ledger effect.”

The long session — cost rises, signal falls5

The same economics as Module 1, over time

  • Everything you leave in the window is re-billed on every later turn. Cost per turn rises even as the work gets simpler.
  • And accuracy falls with it, which is the half people miss — this is a quality problem before it is a cost problem.

Compaction is not the same as clean

  • Compaction keeps a summary of the noise. It shortens the window; it does not remove the dead ends.
  • Useful mid-task. Not a substitute for a fresh session at a task boundary.
The rule: compact within a task, start clean between tasks. A task boundary is a free moment to drop everything that was only ever scaffolding.

Four signals to start clean — and one anti-pattern5

An eval set — six tickets, and a definition of pass6

Why bother

  • “This prompt is better” is an opinion until it is a pass rate. Teams argue about phrasing for months without one.
  • A number turns a taste argument into a disagreement about evidence — which is the kind teams can settle.

The trap in building the set

  • Choosing only tickets your new prompt handles well. Then the set cannot tell you anything — it can only agree with you.
  • Two tickets the weak prompt already passes is what makes the result credible.
This is not research. It is the smallest thing that distinguishes “works” from “does not” — and having any measurement at all puts you ahead of almost every team.

Lab 1.5 — two prompts, six tickets, one number6

What Module 3 hands forwardM3

What you now owe, on every request

  • A shape, not a sentence. Goal, constraints, inputs, output contract, done criteria, stop conditions — and the last is the one you were missing.
  • A source for every constraint. Cite the file, quote before changing, and make refusal a named circumstance.
  • The reusable half in a file. If you typed it twice, it was a skill file the first time.
  • A number before an opinion. Six tickets and a pass rate beats any argument about phrasing.
None of this is about writing longer prompts. Two of the four make your prompts shorter — the standing context and the skill file carry what you were retyping.
Into Module 4: everything here made one agent, in one session, more accurate. Two failures resisted all of it — and neither is fixed by asking better.

AConstraints — a tighter list of what it must not do would have ruled out the reading it picked.
BDone criteria — a stricter definition of finished would have exposed that the requirement was unclear.
COutput contract — specifying the shape of the change would have made the ambiguity visible in review.

Q1 · Answer1 of 8

Two defensible readings; it picked one silently. Which part was missing?
AConstraints.
BDone criteria.
COutput contract.
DStop conditions — a named circumstance requiring it to stop and ask rather than choose.
D. The model has no state it falls back into when it cannot ground an answer — it produces the most plausible continuation. A stop condition installs the missing behaviour: “if more than one reading of the criteria is defensible, stop and ask.” A is the popular answer and the instructive miss: constraints are prohibitions, and a prohibition only helps when you already know what the wrong answer looks like — ambiguity is exactly the case where you do not. B and C constrain the result, and both readings would have satisfied them.

BSilent scope drift.
CInvented API — your build catches it, immediately and every time.

Q4 · The tests are green. What have you actually proven?4 of 8

You asked for a change and its tests in one request. Everything passes. Which action gives you the most additional confidence, for the least effort?
ARun the new test against the code as it was before the change, and confirm it fails.
BAsk the agent to review its own change against the acceptance criteria and report any gaps.
CAsk for additional test cases until coverage of the changed lines reaches your threshold.
DAsk the agent to explain why each assertion is correct, and check the explanations.
Show of hands on each option before advancing · answer on the next slide

Q4 · Answer4 of 8

The tests are green. What gives you the most confidence for the least effort?
ARun the new test against the pre-change code and confirm it fails.
BAsk the agent to review its own change.
CAsk for more cases until coverage hits a threshold.
DAsk it to explain why each assertion is correct.
A. A test that never failed has never demonstrated anything. Running it against the old code is the cheapest way to convert a green tick from a feeling into evidence — and it takes seconds. B and D ask the session that holds the misreading to audit the misreading — you get a fluent confirmation, which feels like verification and is not. C measures which lines ran, not whether anything was asserted about them; a test that asserts nothing still gives you coverage. A reduces the problem rather than removing it — the same misreading survives it, which is what Module 4 is for.

Q5 · Answer5 of 8

Which most reliably means the window is working against you?
ARoughly thirty turns have passed.
BIt re-proposes an approach you already rejected.
CResponses are slower.
DYou have corrected it three times in a row.
B. The window now holds both your rejection and the thing you rejected, and it is weighting them together. No prompt fixes that — the noise is the history itself. A is a proxy for the real thing and a poor one: a focused thirty-turn session can be perfectly clean. C is about response size and load, not signal quality. D is the interesting near-miss — a real signal, but ambiguous, because it might equally mean the task is hard or your request was vague. B is the one that can only mean one thing.

What are the already-passing tickets for?
ATo keep the pass rate from looking low.
BTo give the agent easier examples first.

Q8 · Answer8 of 8

What do the two surviving failures have in common?
AThey involve more code.
BThey occur later, in a noisy window.
CThey need more written into the repository.
DBoth require judging the reading of the requirement — and a session cannot audit its own reading.
D. Both are failures of independence, not of instruction. The implementation and the test come from one reading of the requirement, so they agree with each other whether or not that reading was right — and agreement between two things with the same source proves nothing. A and B describe when these failures are more common, not why they resist instruction. Which is the whole argument for Module 4 — four agents, and the one that reviews the change did not write it.
