Words used in this moduleM3

AI and agent words

  • Agent — Copilot in agent mode. It reads files, edits code and runs commands.
  • Turn — one message from you plus one reply.
  • Context window — everything the agent can see in this chat.
  • Hallucination — a made-up answer that looks real.
  • Grounding — making the agent show where a fact came from.

Course and Global Bank words

  • ADR — a short file that records one design decision (docs/adr/).
  • Acceptance criteria — the checklist in a ticket that defines “done”.
  • Posting — one money movement between accounts.
  • Reversal — undoing a posting. Nothing is deleted.
  • Ledger entry — one saved line of account history. Never edited.

Six parts of a good request — and what goes wrong without each1

The same ticket, asked twice — GB-1511

What most people type
THE ORDINARY REQUESTAdd a reversal endpoint for postings.

What the agent must now guess

  • Should a reversal delete the posting, change it, or add a new one? (The ticket already answers this.)
  • Which files to change.
  • When it is finished, and what to do if unsure.
You cannot see these guesses in the code it writes.
The same request, with the six parts
THE ENGINEERED REQUESTGOAL Add POST /api/v1/postings/{id}/reversal. CONSTRAINTS - Follow docs/conventions.md and .github/instructions/api.instructions.md - A reversal changes the posting's status. It never deletes it. (docs/glossary.md) - Do not store balances. They are calculated. INPUTS - posting/service/PostingService.java - posting/domain/Posting.java - GB-151, all six acceptance criteria - Copy the style of controller/AccountController.java OUTPUT CONTRACT - Controller + service + slice tests - No new dependencies - Errors in ProblemDetail format DONE - mvn test passes; the new test fails on the old code - A second reversal is rejected STOP - If the reversal rules are unclear, stop and ask. Do not choose. - Do not change existing ledger entries.

Stop conditions — tell the agent when to stop and ask1

Make them checkable

  • “Ask if unsure” is too vague.
  • “Ask if no ADR covers this” is clear.

Where to find them

  • Look at the fix-up prompts you typed in Lab 1.1. Each one is a missing stop condition.
Remember: the agent will not tell you what it did not know. A stop condition makes it tell you.

Four prompting patterns — and how to use them with an agent1

Instruction file, skill file, prompt — what goes where2

Common mistakes

  • Steps in the instruction file: it grows too long, and people stop reading it.
  • Facts in the prompt: you type them again every time.

Why a file?

  • Steps in one person’s head leave when that person leaves.
  • In the repo, anyone can review and improve them.

A skill file — the reusable half of a request2

.github/skills/account-change/SKILL.md--- name: account-change description: Implement a change to posting or balance behaviour in global-bank-account metadata: version: "3" owner: payments-platform --- # Before you write anything 1. Read docs/adr/README.md and open any ADR that the ticket touches. 2. Quote the rule you are relying on, and the file it came from. # Rules that always apply - Amounts are stored as long, in paise/cents (ADR-003). - Every posting writes exactly two ledger entries. - Balances are calculated, never stored. - Use slice tests, not @SpringBootTest. # Output contract - Service method + controller + slice tests. - Errors in ProblemDetail format. - No new dependencies without an ADR. # Stop and ask — do not choose - The ticket can be read two ways. - A design choice with no ADR. - Any change to an existing ledger entry.

The header

  • name — must match the folder name.
  • description — Copilot reads this to decide when to use the skill. Be specific.
  • version, owner — so someone keeps it up to date.

The body

  • The six parts from slide 3, minus goal and inputs. Those come with each ticket.
  • “Stop and ask” lists mistakes the team already made once.
Tip: your first version will be too long. Remove lines that do not help on real tickets.

Prompt file or skill?

  • Prompt file — you run it by typing /gb-change. It only fills in the ticket and goal.
  • Skill — Copilot loads it by itself when the task matches its description. The steps live here.

#codebase (older: @workspace)

  • It searches the whole repo for you.
  • Use it once to find the right files. Then name them in your prompt.
Search once to find the files. After that, name them.

Four grounding rules — make the agent show its source3

What grounding means

  • The agent must point to where a fact came from — a file in this repo.

Why it works

  • A guess becomes easy to spot.

Where to put them

  • In the skill file, once. Not in every prompt.
A rule with no clear trigger and no check does nothing.

The same question — with and without grounding3

Without grounding — sounds right
“HOW DO I STOP THE SAME PAYMENT BEING POSTED TWICE?”Ask the caller to send a unique Idempotency-Key header. Save it with the posting. If the same key comes again, return the first posting. This is the usual way for payment APIs.

The problem

  • Good advice in general. Wrong for this repo.
  • No source, so you must check the whole repo yourself.
With grounding — source, code, and the gap
SAME QUESTION, GROUNDING RULES IN THE SKILL FILEIn this repo, duplicates are found by clientReference + valueDate. Source: docs/adr/ADR-007. A header key was rejected: two large upstream systems do not send it when they retry. Existing code: PostingRepository has findByClientReferenceAndValueDate (not used yet). Not found: what to do if the same reference comes with a different amount. No ADR covers it. Stopping to ask.

The pattern

  • Do not write prompt rules for what the build already catches.
  • Spend effort on failures only a person who knows the system can spot.

Tests written to pass — when a green tick proves nothing4

Why it happens

  • You ask for the code and its tests together.
  • Both come from the same understanding of the ticket.
  • If that understanding is wrong, both are wrong — and the tests still pass.

Three warning signs

  • It only checks that no error was thrown.
  • It only checks that a mock was called.
  • It repeats the code’s logic instead of checking the result.

new chat — all you need to typeFollow the account-change skill. Ticket: GB-151 — reverse a posting. Decided: a reversal changes the status. It never deletes. (docs/glossary.md) Rejected: a stored balance column. Do not suggest it again. Done: service method + its test, passing. Next: the controller and its slice test. #file:posting/service/PostingService.java #file:controller/AccountController.java # Rules and ADRs are already in the repo # (Module 2), so they are not repeated here.

Why long chats go wrong

  • The agent re-reads the whole chat on every turn. You pay for all of it.
  • Old mistakes and rejected ideas still affect its answers.

Start a new chat when

  • The ticket is done.
  • It suggests something you already rejected.
  • You cannot remember what is in the chat.
In the new chat, write only what is not in the repo: decisions, rejections, progress.

Test your prompt on six real tickets6

Why

  • “My prompt is better” is an opinion. A pass rate is a fact.

The trap

  • Picking only tickets your new prompt handles well. Then the test can only agree with you.
Six tickets show a trend, not proof. That is still far better than guessing.

What to take into Module 4M3

Do this on every request

  • Use the six parts. Never skip stop conditions.
  • Ask for the source of every rule.
  • Typed it twice? Put it in a skill file.
  • Measure with a pass rate, not a feeling.
Your prompts get shorter. The repo and the skill file carry the rest.
