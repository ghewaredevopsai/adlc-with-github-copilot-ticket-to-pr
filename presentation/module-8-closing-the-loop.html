Seven modules read from the repository. None of them wrote backM8

What this module is

  • The write path. Review, the pull request, and the small amount of documentation worth generating.
  • It closes back to Module 2 — which makes the course a circle rather than a line.

What it is not

  • Not “get the agent to write your documentation”. Most generated documentation is worthless, and half of this module is about what not to write.
The compounding claim: everything so far makes the first ticket go better. This is what makes the second one go better — and that is the only version of this that pays back more than once.

An honest inventory — and the second column is the point1

Four questions for the human — and none of them are in the diff1

Stop doing what the agent already did

  • If the report says the criteria are covered, the scope held and the tests fail against the old code — do not repeat those checks. That is the cheap column.
  • Read the report as an artifact, not a tick. If you cannot tell from it what was checked, that is a finding about your agent definition.
The failure mode: a human who skims the report and signs has not saved time. They have moved the review from one place to nowhere — and the pipeline now reports more confidence than anyone actually has.
The reframe for your team: agent review is not faster review. It is review of different things — and the things left for the human are the ones that were always being skipped.

Reviewing code nobody watched being written2

Three questions for the author — not a gotcha2

The thing not to do

  • Do not ask “did an agent write this?” It is unanswerable in any useful way, it invites a defensive answer, and the reply changes nothing about how you should review the diff.
  • The questions above work regardless of how the code was produced — which is why they survive contact with a team that does not want to be policed.

What good looks like in a team

  • The answers are in the pull request description before anyone asks. That is what the spec and the review report were for.
  • A description that names the deciding constraint and the rejected option is doing the same job as an ADR — and it is where an ADR usually comes from.
The uncomfortable one is the third. If nobody on your team can say what the riskiest part of their change is, that was true before agents — you can just see it now.

Assembly, not judgement — which is exactly its strength3

The one constraint that makes it safe

  • Derived from artifacts, never written freehand. A freehand description is a fluent narrative — and the previous slide was about why those are dangerous.
  • Every claim in the description should be traceable to the spec, the diff or the test report. If it is not in one of those, it is invention.

The tell that yours is freehand

  • It reads beautifully and contains no numbers. No criterion references, no file counts, no test names.
  • A good agent-written description is slightly dull — and checkable line by line.
This is the least controversial thing in the course and the one with the fastest payback: your team writes these by hand today, badly, at the end of the day, when they have stopped caring.

Three things worth generating — and the list nobody needs4

Same three tiers — and one trap specific to pages4

The trap specific to pages

  • Asked to update a page, an agent will very often rewrite the whole page in its own voice. That is technically an edit and practically a replacement — and the previous author's phrasing, caveats and hedges are gone.
  • Those hedges are frequently the most valuable content on the page. “We think, but have not confirmed” does not survive a confident rewrite.

Two guards

  • Append, do not edit. A dated entry under a heading, not a revision of the prose above it.
  • Give it a page it owns. An agent-maintained section, clearly marked, that nobody else writes in — so the blast radius is bounded by construction.
Start read-only here too. Reading Confluence for context is most of the value and needs no write permission at all — and it is a much easier conversation to have first.

The write-back is promotion, not authoring4

spec.md — YOU ALREADY WROTE THIS, IN LAB 2.1## Recommendation Reversal creates a second posting with debit and credit inverted, marking the original REVERSED. ## Why not amend in place glossary.md: reversal is a status change; we do not delete postings. Amending removes the record of what was originally instructed. ## Deciding constraint copilot-instructions.md: balances are derived from entries, never stored.
Every part of an ADR is already here — the decision, the rejected option, and the constraint that decided it. The write-back adds a date, a number and a status.
docs/adr/ADR-011-reversal-as-a-second-posting.md# ADR-011 — Reversal as a second posting Status: Accepted · 2026-03-14 · GB-151 Owner: payments-platform ## Decision A reversal creates a second posting with the debit and credit inverted, and marks the original REVERSED. ## Rejected Amending the original in place - removes the record of what was instructed, and contradicts the glossary's definition of reversal. ## Consequences Two postings exist for one economic event. Reports that count postings must account for this - see GB-207.

The direction matters, and teams get it backwards

  • The ADR lives in the repository, because that is where agents read. The Confluence page is a pointer, for the people who do not read the repository.
  • Put the authoritative copy in Confluence and no agent will ever see it — and the repository gets the stale one.

The loop closes — and this is the only claim about the second ticket5

What actually gets promoted

  • A decision and its rejected option — from the spec, as an ADR.
  • A constraint you had to go and find — the closed ticket, the linked issue, the thing that was not in the description.
  • A drift you discovered — the mirrored type, the stale summary. Fix the document in the same pull request.
Three items, on a ticket that produced any of them. Most tickets produce none, and that is correct — a loop that fires on every ticket is generating noise.
The honest measurement point: you cannot see this on a two-day course. The tally sheet measures the first loop. The second is measured in a quarter, on your own repositories — and the number that shows it is clarifying questions falling in an area somebody documented last month.

Why the loop does not close — and it is not laziness5

Three reasons, none of them about effort

  • The worst possible moment. The ticket is done, the PR is approved, everyone has moved on. The write-back is the last thing standing between somebody and the next thing.
  • Nobody owns it. It is everyone's job, which makes it nobody's, and no retrospective has ever fixed that.
  • Nothing gates it. Nothing blocks, nothing fails, nothing notices. It is the only step in this entire pipeline with no consequence for skipping it.
The fix is the same-PR rule — the knowledge changes in the pull request that produced it. That is the fifth time that rule has answered a different problem in two days: knowledge, skill files, agent definitions, contract documents, and now this.
If you take one operational habit from this course, take that one. It is not the most interesting idea here and it is the one that decides whether any of the rest survives contact with a real quarter.

The first month — and nothing in week one needs permission6

Four numbers, countable in a fortnight with a spreadsheet6

The honest paragraph

  • None of these are clean. They are confounded by which tickets came in, who was on holiday, and whether the quarter was busy.
  • You are looking for direction and magnitude, not significance. A number that halves is telling you something even if you cannot isolate why.

And say this part out loud

  • Having any measurement at all puts you ahead of almost every team doing this. That is not a low bar being celebrated — it is the actual state of the industry.
  • It is also why the tally sheet has been open on the board since the first morning.
Report what you measure, including when it disappoints. That was the promise on slide 8 of Module 1, and it is the reason anything else in this course was worth believing.

The capstone — one ticket, both repositories, every stageCAP

What is being tested

  • Not whether you can do each stage — you have done all eight separately over two days.
  • Whether the stages compose, and where the hand-offs cost you. That is the thing nobody finds out until they run the whole thing.

What goes on the board

  • The six counters, in the last row of the tally sheet, next to row one.
  • Plus one line: which stage cost the most, and was it worth it?
Comparing a careful run to a careless one teaches you nothing about the method. If you flatter the capstone, the only person you mislead is yourself, next quarter, when you try to justify this to your team.

Every outcome is a result — including the disappointing oneCAP

Four things worth keeping — all of them cheapM8

What changed over two days — and what did notM8

What changed

  • The repository answers — so the tax is paid once rather than per request.
  • You make four decisions deliberately on every request that you were making by habit.
  • “Done” is something a machine can check, which is what made delegation safe.
  • The thing that checks the work is not the thing that did it.

What did not

  • The agent is no more capable than it was on Monday morning. Same model, same weights.
  • Every gain came from arranging the work differently — what it can see, what it was asked to optimise, and who checks.
Which is the good news. None of it depends on the next model release, and none of it is invalidated by one.

Your review agent checks the criteria, the scope, the conventions and the tests — and does it well. Why does a human still have to sign?
ABecause the expensive questions — is this the right thing, will it hurt in six months, does it contradict another team — are not reachable from a diff and a list of criteria.
BBecause the agent is not yet reliable enough at those checks to be trusted without oversight.
CBecause accountability cannot be delegated to a tool, whatever the tool's accuracy.
DBecause the agent cannot see the production environment, so it cannot judge operational risk.
Show of hands on each option before advancing · answer on the next slide

Q1 · Answer1 of 8

Why does a human still sign?
AThe expensive questions are not reachable from a diff and a list of criteria.
BThe agent is not reliable enough.
CAccountability cannot be delegated.
DIt cannot see production.
A. On the checks it can do, the agent is often better than a tired human. What it cannot reach is whether this should be built, whether the abstraction will hurt, and whether it contradicts a decision in another team. B is the polite answer and the dangerous one: it implies a better model would remove the need for a human, so a team that believes it stops reviewing when the next model ships. C is true and is not a reason — it says who is responsible, not what they should look at. D is out of scope for this course by design, and would not explain GB-163 either.

CCheck that the test suite is green and that coverage on the changed lines has not dropped.

Q2 · Answer2 of 8

What first?
ARead the description, then check the diff against its claims.
BAsk which parts were agent-written.
CCheck the suite is green and coverage held.
DRead the file list and the diff first — before the description.
D. Once you have read a fluent description you are reviewing that description. The anchoring is well documented in humans and it does not care that you know about it — changing the order is the only reliable counter. A is the sophisticated miss: checking the diff against the description's claims still lets the description set the agenda, so a change it never mentions is never on your list. Silent scope survives A completely. B is unanswerable in any useful way and changes nothing about how you review. C is the check that agrees with itself — Module 3.

AWhat the endpoint does and which fields it accepts.
BAn architecture overview, regenerated every merge.
CA release summary from the merged PRs.
DThe decision, the rejected option, and the constraint that decided it.
D. It is the only one recording something the code cannot. Reading the code tells you what it does; nothing tells you what was considered and ruled out, or why. Always current, always worthless, and now somebody maintains the generator. A is the endpoint definition, retyped. C is the commit log with a different heading.

Q5 · Answer5 of 8

What should it be allowed to do?
ARewrite the page so it is correct.
BEdit only the affected paragraph.
CAppend a dated note under a heading it owns, and flag it for the owner.
DNothing — raise it and let them decide.
C. Additive, reversible, attributed, and it leaves the correction where the next reader of that runbook will actually see it — which a message to a team does not. A is the page-specific trap: asked to update, an agent rewrites in its own voice, and the previous author's hedges — “we think, but have not confirmed” — do not survive a confident rewrite. B is what most teams would configure and it loses the same hedges, in the one paragraph that mattered. D is honourable and it is how a known-wrong runbook stays wrong for a quarter, because raising it competes with everything else on their board.

Why is it skipped?
AIt takes longer than the other steps.
BIt is the only step with no consequence for skipping it.
CEngineers dislike writing documentation.
