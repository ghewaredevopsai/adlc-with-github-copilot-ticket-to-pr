What the review agent catches — and what it cannot1

Four questions for the human reviewer1

Do not repeat the agent’s checks

  • The report says criteria met, scope held, tests fail on old code? Trust it and move on.
  • Read the report properly. If it does not say what was checked, fix the agent definition.
Skim and approve is not a review. Now nobody reviewed it.
Agent review is not faster review. It reviews different things.

Reviewing code nobody watched being written2

Three questions for the author — not a trap2

Do not ask

  • “Did an agent write this?” The answer does not change how you review.

Good teams

  • Answer these in the PR description, before anyone asks.
  • The deciding rule and the rejected option are an ADR in the making.
Nobody can name the riskiest part? That was true before agents too. Now you can see it.

PR descriptions — the agent assembles, it does not judge3

The one rule

  • Every claim must come from the spec, the diff or the test report.
  • Anything else is invented.

Warning sign

  • It reads well but has no numbers: no criteria, no file count, no test names.
A good agent-written description is a bit dull — and every line can be checked.

Three documents worth writing — and four that are not4

Writing to Confluence — the same three levels as Module 64

The trap with pages

  • Asked to update a page, the agent often rewrites all of it in its own words.
  • The author’s careful notes, like “we think, but have not confirmed”, are lost.

Two guards

  • Add, do not edit. A dated entry under a heading.
  • Give it its own section, clearly marked, that nobody else edits.
Start read-only. Reading Confluence gives most of the value, with no write access.

Writing back = promoting the spec, not writing from scratch4

spec.md — YOU WROTE THIS IN LAB 2.1## Recommendation Reversal creates a second posting with debit and credit swapped, and marks the original REVERSED. ## Why not edit in place glossary.md: reversal is a status change; we do not delete postings. Editing removes the record of what was first instructed. ## Deciding rule copilot-instructions.md: balances are calculated from entries, never stored.
Every part of an ADR is already here: the decision, the rejected option, and the deciding rule. Writing back adds a date, a number and a status.
docs/adr/ADR-011-reversal-as-a-second-posting.md# ADR-011 — Reversal as a second posting Status: Accepted · 2026-03-14 · GB-151 Owner: payments-platform ## Decision A reversal creates a second posting with the debit and credit swapped, and marks the original REVERSED. ## Rejected Editing the original in place - removes the record of what was instructed, and breaks the glossary's definition of reversal. ## Consequences Two postings exist for one real event. Reports that count postings must allow for this - see GB-207.

Which copy is the real one?

  • The ADR lives in the repo, because agents read the repo.
  • The Confluence page just links to it, for people who do not read the repo.
  • Keep the real copy in Confluence, and no agent ever sees it.

The loop closes — the next ticket starts from better knowledge5

What to write back

  • A decision and the rejected option → an ADR.
  • A rule you had to hunt for, for example in a closed ticket.
  • A doc you found out of date → fix it in the same PR.
Most tickets produce none of these. That is fine.
You cannot see this in two days. Measure it over three months: fewer clarifying questions in areas someone documented.

Why teams skip the write-back — it is not laziness5

Three reasons

  • Bad timing. The PR is approved and everyone has moved on.
  • No owner. Everyone’s job is nobody’s job.
  • No check. Nothing blocks or fails if you skip it.
The fix is the same-PR rule: update the knowledge in the same pull request. It solved five problems in this course: instruction files, skill files, agent definitions, contract documents — and now this.
Keep one habit from this course? Keep this one.

Your first month — week one needs no permission6

Four numbers you can count in two weeks6

Be honest

  • These numbers are noisy: which tickets came in, holidays, busy weeks.
  • Look for direction and size. A number that halves still means something.

Say this out loud

  • Most teams measure nothing. Any measurement puts you ahead.
Report what you measure, even when it disappoints. That was the promise at Lab 1.1, on the first morning.

The capstone — one ticket, both repos, every stageCAP

What is tested

  • Not each stage — you did each one already.
  • Whether the stages work together, and where hand-offs cost time.

On the board

  • Six counts in the last row of the tally sheet, next to Lab 1.1.
  • Plus: which stage cost most, and was it worth it?
A careful run against a careless one proves nothing. You would only fool yourself.

Four things worth keeping — all of them cheapM8

What changed in two days — and what did notM8

What changed

  • The repo answers questions, so the re-discovery tax is paid once.
  • You make four choices on purpose for each request: task type, mode, context, hand-off.
  • “Done” is something a machine can check.
  • The checker is not the one who did the work.

What did not

  • The model is the same as on Monday morning.
  • Every gain came from how the work was arranged: what the agent sees, what it aims for, and who checks.
Good news: none of this depends on the next model release.
