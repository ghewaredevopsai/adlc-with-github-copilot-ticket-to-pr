Pasting a ticket loses most of itM6

Where we are

  • Module 5 gave you a spec — the written plan for a ticket. Its open questions sit in a file on your laptop.
  • Nobody who can answer them will see them.

This module changes two things

  • What the agent can read — the whole ticket, not one pasted paragraph.
  • Where its questions go — onto the ticket, where people can answer.
Be warned: a connected agent is only as good as your JIRA tickets. Much of this module is about writing better tickets.

Words used in this moduleM6

Connecting the agent

  • MCP (Model Context Protocol) — a standard way to connect an agent to other systems, like JIRA.
  • MCP server — the program that gives the agent those tools.
  • Tool budget — how many tool calls a ticket is worth.
  • Write-back — the agent writing into JIRA: a comment, a link.
  • Unattended — done by the agent with no human check first.

JIRA words

  • Ticket key — the ticket’s ID, like GB-163.
  • Surroundings — comments, linked issues, epic and closed tickets around a ticket.
  • Epic — a group of related tickets.
  • Transition — moving a ticket to a new status.
  • Won’t Do — a status meaning the request was refused.
  • Definition of ready — the team’s checklist before work on a ticket starts.

MCP gives the agent tools, not a database — and the agent picks the calls1

Tool budgets — the call is cheap, the result is not1

Not just cost

  • A big result pushes out what you need — the spec, the two files. Answers get worse.

The habits

  • Pull once. Save a summary in the spec.
  • Never ask it to find a ticket. Give the key.
Warning sign: the agent has read six tickets and written no code. It is searching, and it will keep going.

Four reasons to pull — the fourth matters most1

Cost and correctness

  • Complete. Comments, links, epic and history — where the real rule usually is.
  • Fresh. A paste is a snapshot. It misses answers added later.
  • Traceable. The ticket key goes with the branch, commit and PR.

Behaviour

  • The loop closes. The agent’s questions become comments on the ticket, where people can answer.
The real value is not faster copy-paste. It is that the question reaches someone.

Definition of ready — four additions for agents2

Size tickets by what you can check, not by effort2

Three questions when refining a ticket

  • Can one agent run finish it? If not, it is an epic.
  • Can you check it without the next ticket? Module 5’s task rule, one level up.
  • Where would a mistake get expensive? Split the ticket there.
The cheapest change in this module: smaller tickets, more checkpoints, no tooling needed.

One ticket key, in five places3

Most teams already have

  • The key in the branch, commit and PR title.

Usually missing

  • The spec file, named after the key. Without it, the reasoning is lost in a chat.
  • The write-back — a comment on the ticket with the key. Now the trail goes both ways.
A two-way trail answers “why was it done, and what was rejected?” Regulators ask exactly this.
Easy to enforce: a commit hook and a PR template check for the key.

Five places around a ticket — the description is the least reliable4

The trap — the surroundings can be out of date4

Three ways they mislead

  • Changed in a meeting. The comment says 500 million. The number changed last week.
  • Old link. RISK-402 may already be solved elsewhere.
  • Overturned. An old Won’t Do is evidence, not a final answer.

So: read everything, then rank it

  • Rank by how recent, then by who owns the decision.
  • Cannot rank it? Make it a question — Module 3’s grounding rule.
Trusting an old comment is worse than missing it. The agent becomes confidently wrong.

GB-163 — every check passes, and it breaks a regulation5

The whole ticket
GB-163 — RAISE THE POSTING LIMITRaise the posting limit as discussed with ops. Acceptance criteria - The limit is raised.

If the agent reads only the description

  • It raises MAX_POSTING_MINOR to a number it picked.
  • It adds a test for the new number.
  • It reports the criterion met — and it is met.
Every check passes. The review agent finds nothing, because the criterion is met.
What was in the surroundings all along
FOUR PLACES, NONE OF THEM THE DESCRIPTIONcomment, ops: "up to 500 million so the quarterly rebalancing stops failing" comment, risk: "not without dual approval on anything above the current limit" GB-119, closed Won't Do: "raising the cap without an approval step moves us outside the client money limits agreed with the regulator" epic GB-118: two earlier attempts, both closed for the same reason unanswered, 6 days ago: "is 500m the number, or 500m per instruction with a daily cap?"
The agent is not the problem. The ticket did not contain the rule, and nothing told it to look.

Three changes — the third closes the loop5

“If it stops on every unclear ticket, it will never ship”5

What many stops tell you

  • Your definition of ready is not being used. Now you have proof, per ticket.

What to do

  • Let it stop. Review the stops for two weeks.
  • Tune the noisy ones. Fix the tickets behind the good ones.
Never loosen stop conditions just because stops are annoying. The agent then ships problems instead of finding them.

Three levels of write-back — and one test6

The audit trail — three requirements6

Say this out loud

  • Agents add no new audit work. This is the trail you should already have.
  • Agents just make the gaps visible.

Agree two things first

  • A named service account for the agent — never a person’s login.
  • A fixed comment format, so agent comments are easy to filter.
Do not ask “can the agent write to JIRA?” Ask “can it add a comment, under its own account, that anyone can delete?”

What to take into Module 7M6

Do this on every ticket

  • Pull, do not paste. Name the key and the surroundings.
  • Rank what you find. A disagreement is a question.
  • Post questions on the ticket.
  • Keep write-back to adding things that can be undone. Enforce it with permissions.
