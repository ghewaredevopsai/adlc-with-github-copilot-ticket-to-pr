Words used in this moduleM5

New in this module

  • Spec — a short file (spec.md) that says what “done” means for one ticket.
  • Spec-driven development — write the spec first, then the plan, then the code.
  • Technical plan — how the code will meet the spec (plan.md).
  • Gate — a check by a person between two steps. The answer can be “no”.
  • Spec drift — the code changes, and the spec does not.

Reminders

  • Gate 1 (Module 1) — “Can you say what done means?” Asked before handing a ticket to the agent.
  • The four agents (Module 4) — design, coding, test and review.
  • Value date — the date a posting takes effect, not the date it arrived.
  • Business date — the bank’s working date. It can differ from the calendar date.
  • Minor units — amounts stored in paise or cents.

The chat is thrown away. The spec stays1

Four costs of an unwritten requirement1

Where you pay

  • Re-explaining. The same answer, given in three chats.
  • Review. The reviewer must guess the intent from the code.
  • Handover. The person who knows goes on leave. So does the requirement.
  • Drift. Nobody can say if the code still does what was asked.
None of these comes from the agent or the prompt. They come from the unwritten requirement.
But: many tickets do not need a spec. Section 6 shows which.

Principles → spec → plan → tasks → code, with checks2

Five steps — the output, the check, and who does it2

The spec says what. The plan says how2

A spec with a plan hidden inside
SPEC.MD — WRONGAdd a method findByAccountIdAndValueDateBefore to LedgerEntryRepository. Call it from BalanceService.balanceMinorFor, adding an asAt parameter, and pass the date down from a new query parameter on the controller.

What goes wrong

  • The design is already decided. The plan check has nothing left to decide.
  • The design agent (Module 4) has no options to explore.
  • The ticket writer chose — and may not know each entry has its own valueDate.
The same need, written as a spec
SPEC.MD — RIGHTThe balance for an account as at a date must exclude any posting that has not yet taken effect on that date. Value date is the date a posting takes effect, not the date it arrived - docs/glossary.md. Checkable: a posting dated tomorrow is excluded from today's balance.

The test

  • Could two good engineers read it and write different plans?
  • Yes → it is a spec. No → a plan is hidden inside.
Spec: what must be true. Plan: how we make it true.

Criteria a test can check — and the ones that quietly drop out3

Two short sections nobody writes: out of scope, and assumptions3

What to write

  • Out of scope: things a reader might think are included.
  • Assumptions: every question you answered for yourself.

The rule

  • Mark each assumption confirmed or unconfirmed.
  • An important unconfirmed one blocks the spec check.
Both sections take three minutes. They often prevent the most expensive mistake.

GB-147 — a vague ticket, and the spec it needs3

The ticket, word for word — you have all seen one like it
GB-147 — ADD REPORTING FOR THE OPS TEAMOps need to be able to see what's been posted so they can check things at the end of the day. Can we add a report? Acceptance criteria - Ops can see the postings. Notes Spoke to Priya about this. Should be straightforward.

What an agent does with this

  • It does not refuse. It builds a report.
  • It invents the columns, the date range, and who may see it.
  • It looks finished. The danger is its confidence.
Fifteen minutes of thinking, before any code
SPEC.MD — EXTRACT## Acceptance criteria 1. Given postings on a date, a request for that date returns exactly those, newest first. Postings on other dates: excluded. 2. A date with no postings returns an empty list and 200, not 404. 3. Amounts are in minor units, as everywhere else (ADR-003). 4. Existing endpoints are unchanged. ## Out of scope Export to file. Scheduling. Any change to the consumer. Permissions beyond what the existing endpoints already enforce. ## Assumptions - "End of day" means calendar date, not our business date. UNCONFIRMED - blocking. ## Open questions - Does "posted" include reversed postings? - Which fields does ops actually need? - Is this a screen, or an API for a screen?
Three guesses avoided for fifteen minutes of work. A person answers each in one conversation.

The spec is not just documentation — agents read it3

Why it matters

  • The test agent (Module 4) tests against the acceptance criteria. They come from the spec.
  • The review agent’s check 5, “what is missing?”, needs a list.

So

  • Number your criteria.
  • One behaviour each. An “and” usually means two.

Challenge the plan — four minutes, before any code4

Why now

  • The plan is one page of text. Fixing it is cheap.
  • After coding, the same mistake costs the code, the tests and the review.

Who challenges it

  • The design agent (Module 4). It never sees the code — and there is none yet.
  • Or a colleague, for four minutes.
Do it even when the plan looks obvious. On an unclear ticket, an obvious plan is how a confidently wrong refactor starts.

Task size decides how often you can check4

Why it matters

  • Module 1’s gate 3 asked: can you check the result without reading all of it? Small tasks make that possible.
  • A long agent run can then stop at a step, instead of being undone.

It is not estimation

  • Ask “can I check this alone?”, not “how long will it take?”
Warning sign: every task ends with “…then continue”.

Spec drift — how a spec quietly goes out of date5

Three checks CI can run today

  • 1 · The diff changes a file the spec names, but not the spec → ask for a note in the PR.
  • 2 · Every numbered criterion has a test that mentions it → otherwise the build fails.
  • 3 · Every file the spec names still exists.
These checks show the spec was looked at. They cannot show it is correct.
Keep the spec in the repo, next to the code. A spec in a wiki needs a second, separate update — and that update rarely happens.

Two ways to catch drift in a pull request5

1 · Tag each test with the criterion it proves
PostingReportTest.java/** Spec GB-147 AC2: a date with no postings returns an empty list and 200. */ @Test void returnsEmptyListForADateWithNoPostings() { ... }
ci/check-criteria-covered.sh# every numbered criterion in the spec must be # referenced by at least one test, or fail. grep -o 'AC[0-9]*' spec.md | sort -u > wanted grep -ro 'AC[0-9]*' src/test | sort -u > have comm -23 wanted have | grep . && exit 1
  • “Covered” in the test report becomes a fact the build checks.
2 · Three lines in the pull request template
.github/pull_request_template.md## Spec Link: <path to spec.md> - [ ] The spec still describes what this code does. If not, it is updated in this PR. - [ ] Criteria added or changed are listed here. - [ ] Out-of-scope list still holds — nothing in this diff is outside it.
  • CI catches a missing test. The template makes a person think — one sentence per PR.
  • Same idea as Module 2: “does this change make anything in docs/ wrong?”
The limit: this catches drift. It cannot catch a spec that was wrong from day one. The human checks are for that.

When a spec is too much — and the thirty-second version6

The thirty-second version — three lines at the top of the ticket
THE THIRTY-SECOND SPECDone when: a request for a date returns that date's postings, newest first; an empty date returns 200 and an empty list. Not doing: export, scheduling, permissions. Assuming: calendar date, not business date.

Why it is enough

  • It has the three parts that matter: criteria, out of scope, assumptions.
  • It lives in the ticket, so there is no second file to drift.
Three lines for most tickets. The full process only for the unclear or risky few.

What to take into Module 6M5

For each ticket

  • Decide if it needs a spec. Most get three lines.
  • Write criteria a test can check. Number them.
  • List what is out of scope, and what you assumed.
  • Challenge the plan before any code.
The spec is where the four agents get their facts. Without it, they check against nothing.
