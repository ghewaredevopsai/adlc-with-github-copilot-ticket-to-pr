What this module is not

Why this is the hinge of the course

  • This is about being able to tell it something worth doing — and about knowing, before any code exists, whether you can.

The transcript is disposable. The spec is the artifact1

Four costs, and you have paid all four1

Where the cost shows up

  • Re-clarification. The same question answered three times in three sessions, because the answer only ever lived in a window that got compacted.
  • Review. A reviewer handed a diff and no spec has to reconstruct intent from the code — which is the confidently wrong refactor, seen from the other side.
  • Handover. The person who holds the requirement goes on leave, and it goes with them.
  • Drift. Nobody can tell whether the code still does what was asked, because what was asked is not written down anywhere checkable.
Every one of these is a cost of the requirement being unwritten — not a cost of the agent, the model, or the prompt. No amount of Module 3 touches any of them.
And yet: prompt-first is right for a great many tickets. Section 6 says which, and it matters — a room that leaves believing every ticket needs a spec will abandon this within three weeks.

The boundary people get wrong — and it makes specs useless2

A spec that has smuggled a plan into it
SPEC.MD — WRONGAdd a method findByAccountIdAndValueDateBefore to LedgerEntryRepository. Call it from BalanceService.balanceMinorFor, adding an asAt parameter, and pass the date down from a new query parameter on the controller.

What this has destroyed

  • The design gate has nothing left to decide — the decision was taken in the document that was supposed to state the problem.
  • Yesterday's design agent has nothing to explore, so it produces a rationalisation instead of options.
  • And the choice was made by whoever wrote the ticket, who may not have known the entry carries its own valueDate.
The same requirement, stated as a requirement
SPEC.MD — RIGHTThe balance for an account as at a date must exclude any posting that has not yet taken economic effect on that date. Value date is the date of economic effect, not the date of receipt - docs/glossary.md. Verifiable: a posting dated tomorrow is excluded from today's as-at balance.

The test that separates them

  • Could two competent engineers read this and produce genuinely different plans?
  • If yes, it is a spec. If no, a plan has been smuggled in — and the design stage has been deleted without anyone deciding to delete it.
Spec: what must be true. Plan: how we will make it true. Only one of the two is a decision, and it is the one that belongs to the engineer.

Criteria a test can check — and the ones that quietly drop out3

Two sections nobody writes, and both are cheap3

Where the content comes from

  • Out of scope — write the things a reasonable reader might think are included. If nothing comes to mind, the ticket is smaller than you think or you have not read it carefully.
  • Assumptions — every question you answered for yourself while writing the spec. Each one is an assumption whether you name it or not.

The rule that makes assumptions work

  • Mark each one confirmed or unconfirmed. An unconfirmed assumption on a material point is a blocking item at the spec gate, not a footnote.
  • That is the mechanism by which a spec stops the agent inventing: the open question is raised at the gate rather than resolved silently in a diff.
Both sections take three minutes. They are skipped because they feel like paperwork, and they are the two that most often prevent the expensive mistake.

GB-147 — eight words, and what they have to become3

The ticket, verbatim — and you have all been handed this one
GB-147 — ADD REPORTING FOR THE OPS TEAMOps need to be able to see what's been posted so they can check things at the end of the day. Can we add a report? Acceptance criteria - Ops can see the postings. Notes Spoke to Priya about this. Should be straightforward.

What an agent does with this

  • It does not refuse. It produces a report — with columns somebody invented, a date range somebody invented, and no permission model at all.
  • And it looks finished. That is the failure: not a bad output, a confident one.
Fifteen minutes of thinking, before any code
SPEC.MD — EXTRACT## Acceptance criteria 1. Given postings on a date, a request for that date returns exactly those, newest first. Postings on other dates: excluded. 2. A date with no postings returns an empty list and 200, not 404. 3. Amounts are returned in minor units, as everywhere else (ADR-003). 4. Existing endpoints are unchanged. ## Out of scope Export to file. Scheduling. Any change to the consumer. Permissions beyond what the existing endpoints already enforce. ## Assumptions - "End of day" means calendar date, not our business date. UNCONFIRMED - blocking. ## Open questions - Does "posted" include reversed postings? - Which fields does ops actually need? - Is this a screen, or an API for a screen?
Three invented decisions avoided, for fifteen minutes, before a line of code existed — and each one is a question a human answers in a single conversation.

The spec is not documentation — it is an agent's input3

Why this makes it more than good practice

  • Yesterday the test agent's stated source of truth was the acceptance criteria. This is where those come from.
  • The review agent's fifth check — what is missing — is unanswerable without an enumerated list to check against.

The practical consequence

  • Number your criteria. The numbering is not cosmetic — it is what makes a report line traceable to a requirement.
  • One criterion per line, one behaviour per criterion. A criterion containing “and” is usually two.
The whole Day 1 pipeline was waiting for this. Four independent agents checking against a vague requirement produce four confident, independent, unverifiable opinions.

Challenging the plan — four minutes, before any code4

Why here, and not at review

  • Right now the plan is a page of text. A wrong direction costs a rewrite of a page.
  • After implementation the same wrongness costs a change set, its tests, its review, and the conversation about whether it is worth redoing — which is usually lost.

Who does the challenging

  • Yesterday's design agent is the natural challenger: it is defined as blind to the implementation, and here there is no implementation. Its independence costs nothing at this stage.
  • Or a colleague, for four minutes. The cost is trivial either way; the reason it does not happen is that nobody scheduled it.
Do not skip this when the plan looks obvious. An obvious plan on an ambiguous ticket is the exact shape of the confidently wrong refactor — obviousness is a property of your reading, not of the problem.

Task size is not an estimate — it is how often you get to check4

Why this connects to delegation

  • Module 1's gate 3 asked whether success could be checked without reading all of it. Small checkable tasks are how that becomes true.
  • A long unattended run is safe when it can be stopped at a boundary rather than unwound from the end.

What this is not

  • Not estimation. Not story points. The question is “can I check this on its own?”, not “how long will it take?”
  • Two tasks of equal effort can differ completely in checkability — and that is the property that matters here.
The tell: if your plan's tasks each end with “…then continue”, you have written a narrative, not a breakdown.

Drift — where every specification practice quietly dies5

Three drift checks CI can run today

  • 1 · A changed behaviour with an unchanged spec. If the diff touches a file the spec names and the spec is untouched, ask for a sentence in the PR. Not a block — a question.
  • 2 · Every criterion has a test that references it. Number the criteria, tag the tests, and a missing number is a failing build.
  • 3 · The spec's named files still exist. Catches the spec that survived a refactor — the cheapest check and the most frequently triggered.
None of these verifies the spec is correct. They verify it has been looked at — which is all a machine can do, and considerably more than nothing.
Where the spec lives matters: in the repository, next to the code, in the same pull request. A spec in a wiki drifts because updating it is a second, separate act — and second acts do not happen.

Making the checks real — two mechanics5

1 · Tag tests with the criterion they prove
PostingReportTest.java/** Spec GB-147 AC2: a date with no postings returns an empty list and 200. */ @Test void returnsEmptyListForADateWithNoPostings() { ... }
ci/check-criteria-covered.sh# every numbered criterion in the spec must be # referenced by at least one test, or fail. grep -o 'AC[0-9]*' spec.md | sort -u > wanted grep -ro 'AC[0-9]*' src/test | sort -u > have comm -23 wanted have | grep . && exit 1

What this buys

  • The Module 4 test report becomes mechanically verifiable — “covered” is now a fact the build checks, not a claim the agent makes.
2 · Three lines in the pull request template
.github/pull_request_template.md## Spec Link: <path to spec.md> - [ ] The spec still describes what this code does. If not, it is updated in this PR. - [ ] Criteria added or changed are listed here. - [ ] Out-of-scope list still holds — nothing in this diff is outside it.

Why the template is the half that works

  • The CI check catches omission. The template catches judgement — and it costs a reviewer one sentence.
  • It is the same intervention Module 2 recommended for knowledge: “does this change make anything in docs/ wrong?”
The honest limit: all of this catches drift. None of it catches a spec that was wrong on day one — that is what the gates are for, and no automation replaces them.

When this is overkill — and the thirty-second version6

The lighter mechanic — three lines at the top of the ticket
THE THIRTY-SECOND SPECDone when: a request for a date returns that date's postings, newest first; an empty date returns 200 and an empty list. Not doing: export, scheduling, permissions. Assuming: calendar date, not business date.

Why this captures most of the value

  • It is the three sections that do the work — verifiable criteria, out of scope, stated assumptions. Everything else in the chain is scaffolding around these.
  • It fits in the ticket, so there is no second artifact to drift.
  • And it still gives the test agent something to work from, and the reviewer something to check against.
Getting the proportion right is the whole game. A team that writes a full spec for everything abandons the practice within a month; a team that writes three lines for everything and a full chain for the ambiguous minority keeps it for years.

What fifteen minutes buys — priced honestly6

What Module 5 hands forwardM5

What you now owe, per ticket

  • Decide whether this ticket needs a spec at all. Three tests, and most tickets fail all three — those get three lines.
  • Write criteria a test can check. Numbered, one behaviour each, naming an input and an observable outcome.
  • State what is out, and what you assumed. An unconfirmed assumption on a material point blocks the gate.
  • Challenge the plan before code exists. Four minutes, and question four is the one that finds things.
The spec is where yesterday's four agents get their source of truth. Without it they check confidently against nothing.
Into Module 6: your spec is a file on your laptop, written from a ticket somebody pasted into a chat. The criteria live in JIRA, and the questions you raised belong back on the ticket — where the person who can answer them will see them.

Q3 · Answer3 of 8

Which one could become a failing test from that sentence alone?
A“Usable without training.”
B“Must not degrade performance.”
C“All existing behaviour preserved exactly.”
D“A date with no postings returns 200 and an empty list” — an input and an observable outcome.
D. It names an input (a date with no postings) and an observable outcome (200, empty list). That is the whole bar. C is the instructive miss because it sounds like the most rigorous option here. BImplement both behaviours behind a flag, so whichever answer arrives is already supported.

DLeave it out of the spec and raise it in the pull request, where the reviewer will have more context.

Q4 · Answer4 of 8

A material assumption you cannot confirm.
APick the likelier reading and note it.
BImplement both behind a flag.
CMark it blocking at the spec gate — it does not pass until someone who can answer does.
DLeave it out and raise it in the PR.
C. That is what the gate is for. Writing the assumption down gives the gate something to bite on; marking it blocking is what converts a note into a decision somebody has to make. A is the popular answer and the precise failure is this: a note in a document nobody is required to act on is not a mechanism, it is a hope. B is more work than the conversation you are avoiding, and it ships a flag you own forever. D raises it at the most expensive moment — after the code exists, when changing the answer means changing the change set.
