Module 1 — The ADLC operating model & token economicsM1

The problem

  • The agent is fast, but it re-learns what your team already knows.
  • You pay twice: in AI credits, and in wrong answers.
Next: Module 2 writes that team knowledge into the repository.

Module 1 labs — what you do, what you learnM1

Lab 1.1 · The baseline run

GB-142 · 35 min + record

You do

  • Fix GB-142 (retried payments are booked twice) on the repo as it is.
  • Use the same scripted prompt as everyone. Repair only when a check fails.

You learn

  • How much of a run is re-discovery, measured, not guessed.
  • The assumptions list shows what your team never wrote down.
You leave with: the fix, and metrics-1.1-*.md

Module 2 — Knowledge harnessingM2

The problem

  • Lab 1.1 showed the agent re-learning team facts.
  • Write them into the repo once. The agent reads them on every request.
Next: Module 3 is about how you ask.

Module 2 labs — what you do, what you learnM2

Lab 2.1 · Write the knowledge in three layers

GB-142 · 45 min

You do

  • List what the agent re-discovered in Lab 1.1.
  • Write a repo instruction file, a path-scoped file and an ADR.

You learn

  • Cutting the file down is part of the job: 30 lines or fewer.
  • An ADR holds what the code cannot show: the rejected option.
You leave with: three files, committed on lab-2.1-knowledge

Lab 2.2 · The same ticket, re-measured

GB-142 · 45 min

You do

  • Run GB-142 again: same prompt, new chat, your updated repo.
  • First check that Copilot really loads your files.

You learn

  • Only the repo changed, so the two rows compare fairly.
  • Look at which column moved. That tells you what to write next.
You leave with: metrics-2.2-*.md

Module 3 — Prompt and context engineeringM3

The problem

  • The repo now says what is true. This module is how you ask.
  • An agent always answers, even when it does not know.
Next: Two failures remain. Module 4 adds a separate checker.

Module 3 labs — what you do, what you learnM3

Lab 3.1 · The skill file

GB-151 · 45 min

You do

  • Write a six-part request for GB-151.
  • Save the reusable half as SKILL.md, and a /gb-change prompt file.

You learn

  • A skill file names no ticket. It holds steps true for every ticket.
  • Check that Copilot loads it. An unused file does nothing.
You leave with: SKILL.md and gb-change.prompt.md, committed

Lab 3.2 · The prompt A/B

GB-204, 205, 206 · 45 min

You do

  • Write the pass criteria first.
  • Run three tickets twice: an ordinary prompt (A), then /gb-change (B).

You learn

  • Three tickets make a small eval set with a pass rate you can compare.
  • Column A must not see the skill file, or it is not a fair control.
You leave with: two pass rates out of 3, in metrics-3.2-*.md

Module 4 — Specialised agentsM4

The problem

  • One agent writes the code and the test from one reading of the ticket.
  • So they always agree, and the agreement proves nothing.
Next: Day 2 asks: what does done mean? Module 5.

Module 4 labs — what you do, what you learnM4

Lab 4.1 · Two agent definitions

No ticket · 45 min

You do

  • Write test.agent.md and review.agent.md with all seven parts.
  • Write down the input each agent must not see.

You learn

  • What an agent is not given matters as much as what it is told.
  • Audit each file, then check VS Code lists both agents.
You leave with: two agent files, committed

Lab 4.2 · The four-agent hand-off

GB-207 · 45 min

You do

  • Chat 1: design, then coding. Chat 2: test, from the ticket only.
  • Chat 3: review, trying to prove the change wrong.

You learn

  • Separate chats keep each check independent.
  • You record whether the agents disagreed. A disagreement is a finding.
You leave with: four files in specs/, and a verdict

Module 5 — Spec-driven developmentM5

The problem

  • Every agent works from the ticket as written.
  • A vague ticket gives a confident, wrong change.
Next: Module 6 moves the open questions onto the ticket.

Module 5 labs — what you do, what you learnM5

Lab 5.1 · Write the spec for GB-147

GB-147 · 45 min

You do

  • Let Copilot interview you, then draft numbered criteria.
  • Add out of scope, assumptions, open questions. Then gate it.

You learn

  • Do not let the agent build it first “to see”.
  • A spec that names code is hiding a plan. Look for it.
You leave with: specs/GB-147.md, committed and reviewed

Lab 5.2 · Plan, challenge, gate

GB-147 · 30 min

You do

  • The design agent writes the plan from your spec. Challenge it.
  • Split it into tasks you can check, then gate the task list.

You learn

  • A challenge costs minutes now, and saves rework later.
  • Task size decides how late you find a mistake.
You leave with: specs/GB-147-plan.md with tasks and your gate decision

Module 6 — The ticket as the unit of workM6

The problem

  • A pasted ticket is one paragraph, copied once.
  • Comments, links, the epic and later answers are left out.
Next: Module 7 crosses from one repo to two.

Module 6 labs — what you do, what you learnM6

Lab 6.1 · The connected run

GB-207 · 40 min · solo

You do

  • Set a tool budget, then pull GB-207 by its key.
  • Save it as a spec, code it, write back one comment.

You learn

  • What the connection costs, counted in calls.
  • What a safe, undoable write-back looks like.
You leave with: specs/GB-207.md, a commit, one comment

Lab 6.2 · GB-163: raise the posting limit

GB-163 · 50 min · pairs

You do

  • Part A: work it from the pasted description only.
  • Part B: pull the whole ticket, then compare the two.

You learn

  • What a small-looking ticket leaves out when pasted.
  • Do Part A first, and do not open the ticket early.
You leave with: a verdict for Part A, a record of Part B

Module 7 — Multi-repo engineeringM7

The problem

  • Across two repos nothing errors, and the tests still pass.
  • The agent sees half the system, and does not know it.
Next: Module 8: what you learned is about to be forgotten.

Module 7 labs — what you do, what you learnM7

Lab 7.1 · Cross-repo GB-158, contract first

GB-158 · 30 min

You do

  • Write the contract change, then ship the producer side.
  • Additive only, then write two linked PR descriptions.

You learn

  • main stays green in both repos after every merge.
  • The plan lives in the PR text, not only in the code.
You leave with: a contract change, a green producer branch, two PR texts

Lab 7.2 · Review a cross-repo change set

GB-158 · 45 min

You do

  • Review a prepared change three times: producer, consumer, both.
  • Review only. Do not fix or merge anything.

You learn

  • Which inputs let a one-repo review see the other repo.
  • Compare your three review reports side by side.
You leave with: three review reports and a comparison table

Module 8 — Closing the loopM8

The problem

  • Modules 3 to 7 read the repo. None of them wrote back.
  • So the next ticket starts from zero again.
Next: The capstone runs one ticket through every stage.

Module 8 labs — what you do, what you learnM8

Lab 8.1 · Close the loop

GB-151 · 15 min

You do

  • Write one ADR: the choice, the rejected option, the deciding rule.
  • Fix one document the work made wrong. One commit.

You learn

  • Test each candidate: can an engineer work it out from the code?
  • If yes, do not write it.
You leave with: one ADR and one corrected document

Capstone · GB-186, every stage

GB-186 · 50 + 20 min

You do

  • Payroll batch posts all-or-nothing, across both repos.
  • Eight stages, ten chats: pull, spec, plan, build, test, review, PRs, write-back.

You learn

  • How the stages fit, and where hand-offs cost time.
  • Compare asked, rework and churn per criterion with Lab 1.1.
You leave with: two branches, the write-back, metrics-capstone-*.md
