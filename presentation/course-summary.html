Module 1 — The ADLC operating model & token economicsM1

The problem

  • The agent is fast. But every new chat starts from zero.
  • It spends time learning what your team already knows.
Next: Module 2 writes team knowledge into the repo.

Module 1 labs — what you do, what you learnM1

Lab 1.1 · The first run

GB-142 · 35 min + record

You do

  • Fix GB-142: a retried payment is booked twice.
  • Everyone uses the same prompt, on the repo as it is.

You learn

  • How much of the work is the agent re-learning.
  • Its guesses show what your team never wrote down.
You leave with: the fix, and metrics-1.1-*.md

What you write down

  • Copilot counts turns, tool calls, questions, repairs and wasted lines.
  • You read the model, tokens and AI credits in Copilot.
  • You count the same way in Lab 2.2 and in the capstone.

Module 2 — Knowledge harnessingM2

The problem

  • In Lab 1.1 the agent re-learned what the team knows.
  • Write it in the repo once. The agent reads it every time.
Next: Module 3 is about how you ask.

Module 2 labs — what you do, what you learnM2

Lab 2.1 · Write the knowledge down

GB-142 · 45 min

You do

  • List what the agent had to learn in Lab 1.1.
  • Write three files: team rules, folder rules, one ADR.

You learn

  • Short is better: the main file is 30 lines or fewer.
  • An ADR keeps what the code cannot show.
You leave with: three files, committed

Lab 2.2 · Run the same ticket again

GB-142 · 45 min

You do

  • Fix GB-142 again, with the same prompt, in a new chat.
  • First check that Copilot reads your new files.

You learn

  • Only the repo changed, so the numbers compare fairly.
  • The number that changed shows what to write next.
You leave with: metrics-2.2-*.md

Module 3 — Prompt and context engineeringM3

The problem

  • The repo now holds the facts. Next: how do you ask?
  • The agent always answers, even when it does not know.
Next: Two problems remain. Module 4 adds a second agent to check.

Module 3 labs — what you do, what you learnM3

Lab 3.1 · Write a skill file

GB-151 · 45 min

You do

  • Write a clear six-part request for GB-151.
  • Save the part you will reuse as a skill file.

You learn

  • A skill file works for every ticket, not just one.
  • Check that Copilot loads it.
You leave with: SKILL.md and gb-change.prompt.md

Lab 3.2 · Test the prompt

GB-204, 205, 206 · 45 min

You do

  • Decide what counts as a pass, before you start.
  • Run three tickets twice: a plain prompt, then your skill file.

You learn

  • Three tickets give a score you can compare.
  • Keep the plain run away from the skill file.
You leave with: two scores out of 3, in metrics-3.2-*.md

Module 4 — Specialised agentsM4

The problem

  • One agent writes both the code and the test.
  • Both come from one reading of the ticket, so they always agree.
Next: Day 2 starts with: what does “done” mean?

Module 4 labs — what you do, what you learnM4

Lab 4.1 · Write two agent files

No ticket · 45 min

You do

  • Write a test agent file and a review agent file.
  • For each one, write what it must not see or do.

You learn

  • What an agent cannot see keeps its check honest.
  • Check that VS Code shows both agents.
You leave with: two agent files, committed

Lab 4.2 · One ticket, four agents

GB-207 · 45 min

You do

  • Chat 1: design, then code. Chat 2: test, from the ticket.
  • Chat 3: review, and try to prove it wrong.

You learn

  • Separate chats keep each check separate.
  • If agents disagree, you found something to look at.
You leave with: four files in specs/, and your verdict

Module 5 — Spec-driven developmentM5

The problem

  • Every agent works from the ticket as written.
  • A vague ticket gives a wrong change that looks right.
Next: Module 6 puts the open questions on the ticket.

Module 5 labs — what you do, what you learnM5

Lab 5.1 · Write a spec

GB-147 · 45 min

You do

  • Let Copilot ask you questions about GB-147.
  • Write numbered checks, what is out, and open questions.

You learn

  • Do not let the agent build it first “to see”.
  • A spec should not decide the code.
You leave with: specs/GB-147.md

Lab 5.2 · Plan it and check the plan

GB-147 · 30 min

You do

  • The design agent writes a plan from your spec.
  • You question it, then split it into small tasks.

You learn

  • Questioning a plan is cheap. Fixing code is not.
  • Small tasks let you find mistakes early.
You leave with: specs/GB-147-plan.md, with tasks

Module 6 — The ticket as the unit of workM6

The problem

  • People copy a ticket into the chat.
  • The copy misses comments, links and later answers.
  • MCP is a standard way to connect an agent to tools like JIRA.
Next: Module 7 moves from one repo to two.

Module 6 labs — what you do, what you learnM6

Lab 6.1 · Fetch the ticket

GB-207 · 40 min · alone

You do

  • Set a tool-call limit. Fetch GB-207 by its key.
  • Save it as a spec, build it, post one comment.

You learn

  • What the JIRA link costs, in tool calls.
  • What a safe comment back looks like.
You leave with: specs/GB-207.md, a commit, one comment

Lab 6.2 · Copy or fetch?

GB-163 · 50 min · in pairs

You do

  • Part A: work only from the copied description.
  • Part B: fetch the whole ticket. Then compare.

You learn

  • What a copy of a ticket leaves out.
  • Do Part A first. Do not open the ticket early.
You leave with: your notes on Part A and Part B

Module 7 — Multi-repo engineeringM7

The problem

  • Some changes touch two repos.
  • The agent sees one repo, and does not know the other exists.
Next: Module 8: keep what you learned.

Module 7 labs — what you do, what you learnM7

Lab 7.1 · Change the API first

GB-158 · 30 min

You do

  • Write the API change down first.
  • Build the API side by only adding. Write two PR texts.

You learn

  • Both repos keep working after each merge.
  • The PR text explains the plan.
You leave with: an API change note, a working branch, two PR texts

Lab 7.2 · Review a two-repo change

GB-158 · 45 min

You do

  • Review a ready change three ways: API side, caller side, both.
  • Only review. Do not fix anything.

You learn

  • What a review of one repo can see.
  • Compare your three reviews.
You leave with: three reviews and a table

Module 8 — Closing the loopM8

The problem

  • Modules 3 to 7 read the repo but never wrote to it.
  • So the next ticket starts from zero again.
Next: The capstone runs one ticket through every step.

Module 8 labs — what you do, what you learnM8

Lab 8.1 · Save one lesson

GB-151 · 15 min

You do

  • Write one ADR from GB-151.
  • Fix one doc that the work made wrong.

You learn

  • Ask: can someone see this in the code?
  • If yes, do not write it down.
You leave with: one ADR and one fixed doc

Capstone · One ticket, every step

GB-186 · 50 + 20 min

You do

  • A payroll batch must save all payments, or none.
  • Take it through every step, in both repos, in ten chats.

You learn

  • How all the steps fit together.
  • How your numbers compare with Lab 1.1.
You leave with: two branches, the saved lessons, metrics-capstone-*.md
